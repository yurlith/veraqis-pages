What is actually wrong with your archive

A ZIP is not one blob. It is a sequence of stored files, each with its own header and its own checksum, followed by an index at the very end that lists where everything is. Damage almost never destroys all of that at once — it destroys one part of it. Which part decides everything about what you can get back.

Most tools report a single verdict: the archive opens, or it does not. That verdict throws away the information you need. An archive can be unopenable and still contain fifty perfectly intact files.

The index is damaged

The archive will not open at all, but the files themselves are usually untouched. This is the most recoverable case there is — and it is the most common one.

How VERAQIS reads a damaged ZIP

A working ZIP reader starts at the end, reads the central directory, and trusts it. That is fast and correct for a healthy file — and useless for a damaged one, because the index is the part most likely to be missing.

VERAQIS reads the archive the other way round.

Local file headers

Every entry in a ZIP is preceded by its own local file header, carrying the signature PK\x03\x04, the entry's name, its compressed and uncompressed sizes, and a CRC-32 of the original contents. These headers are spread throughout the archive, next to the data they describe. Damage at the end of the file does not touch them.

Scanning for those signatures reconstructs the archive's contents without consulting the index at all. This is why a missing central directory is usually survivable: the information it held is duplicated, entry by entry, right next to each entry.

When the central directory is damaged or missing

The index is rebuilt from what the local headers prove — not invented. Where a header and the surviving index disagree, the actual bytes decide: if the data on disk contradicts a stored value, the stored value is not emitted. An entry whose header is itself destroyed is reported as unrecoverable rather than reconstructed from a plausible guess.

What CRC validation settles

Each entry carries a CRC-32 computed when the archive was written. After decompression, VERAQIS recomputes it. A match is strong evidence that these are the original bytes: random corruption has roughly a one-in-four-billion chance of still matching.

An honest limit. CRC-32 proves that bytes did not change by accident. It is not a cryptographic guarantee and it is not tamper-proof — we built archives whose contents differ from the original but whose CRC-32 still matches, and the standard tools call them healthy. Accidental damage is what a CRC catches, and that is what it is used for here.

Recovered, damaged, unknown — kept separate

The single design decision behind this product: a result is only called verified when something independent of the repair confirms it. A structural fix does not get to certify its own output.

LabelWhat it meansWhat proved it
Verified These are the original bytes. The entry decompressed cleanly and its stored CRC-32 matched.
Damaged The entry exists but its contents changed. The entry decompressed, but the CRC-32 did not match.
Unknown We cannot say either way. No surviving evidence settles it — a destroyed header, an unreadable region.
Lost The data is not in the file. The bytes are absent — truncated away or overwritten.

Unknown is a legitimate result. A report that says "43 files verified, 2 damaged, 1 unknown" is more useful than one that says "repaired!" and leaves you to discover which documents are quietly wrong.

The full definition of what counts as evidence — and the rule that a checksum a repair was fitted to proves nothing — is written up in the evidence model.

What this cannot do

Every recovery tool has these limits. Most do not print them.

  • Data that is gone stays gone. If the bytes were truncated away or overwritten, no analysis returns them. The region is reported as lost.
  • No password recovery, no encryption bypass. Encrypted archives are detected and reported. VERAQIS does not guess, derive, enumerate or brute-force a password, and does not remove access controls. The unencrypted structure around an encrypted payload can be repaired without touching the payload.
  • A compressed stream can fail as a unit. Where a format ties later bytes to earlier ones, damage can cost more than it physically destroyed. What survives is then a measurement, not an assumption — we measured it per format.
  • A verified entry is verified against accidental damage. CRC-32 is not a tamper-proof signature. For deliberate modification you need an independent cryptographic witness, not the archive's own checksum.
  • Formats beyond ZIP are experimental. PDF, SQLite, TAR/GZIP, 7z and RAR handling exists and is measured, but it is not a stable commercial promise. The format reference states the position for each one.
  • Analysis is free and always will be. You can see the full verdict on your archive before deciding whether the result is worth anything to you.
Before you try anything, on any tool: work on a copy. Keep the original file untouched and unmodified somewhere safe. A repair that overwrites your only copy can turn a recoverable archive into an unrecoverable one, and that is a far more common way to lose data than the original damage. VERAQIS opens sources read-only for exactly this reason.

Your files do not leave your machine

Recovery runs locally. There is no upload step, no account, and no telemetry — not as a setting you can turn on, but as an absence of the code that would do it.

This matters more than it sounds. A damaged archive is often the one containing something you cannot replace and would rather not hand to a stranger: financial records, client work, legal documents, photographs. Uploading it to a web repair service means giving an unknown operator a copy of exactly that.

Common questions

Can VERAQIS recover any corrupted ZIP file?

No. Recovery depends entirely on what survived. If the bytes of a file are gone, no tool can return them, and VERAQIS reports that region as lost rather than filling it in. What VERAQIS does guarantee is the opposite direction: it does not report a file as recovered unless the archive's own checksum confirms it.

Are my files uploaded to a server?

No. Analysis and recovery run on your own machine. The source archive is opened read-only and never modified, and recovered output is written to a destination you choose.

What does verified recovery mean?

A file is only labelled verified when a check independent of the repair confirms it — for a ZIP entry, the CRC-32 that was stored when the archive was created. A structural repair does not make its own result true, so the checksum has the last word.

Can VERAQIS open a password-protected or encrypted archive?

Encrypted archives are detected and reported, and recovery stops there. VERAQIS does not guess, derive or brute-force passwords, and it does not bypass encryption. The unencrypted structure around an encrypted payload can still be repaired without touching the payload.

Is VERAQIS Recovery available for Windows today?

Not yet. VERAQIS Recovery for Windows is pending a signed store release and is not publicly downloadable. No unsigned build is published. The Android archive inspector is available now and is release-key signed.
