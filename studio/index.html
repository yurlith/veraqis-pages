What this browser can do

What Studio does

Studio is the workspace form of the ZIP integrity check. The quick checker answers one question about one file. Studio keeps the result as a project you can name, save, export, re-open and compare — still without a server.

  • Analyse a ZIP archive: end-of-central-directory record, central directory, local file headers, entry boundaries, overlaps, truncation and per-entry CRC-32.
  • Classify every entry as verified, structurally valid, potentially recoverable, damaged or unknown — each with the reason that produced it.
  • Keep the result as a local project, if you ask for it.
  • Download one verified entry at a time, revalidated after extraction — see Download individually verified files below.
  • Export a machine-readable JSON report, a standalone HTML report, or the whole project as a portable file.
  • Re-open a report later, on any machine, without the original archive.

How local processing is enforced

"Nothing is uploaded" is a claim worth checking rather than trusting. Four things make it true here, and you can verify each yourself:

  • There is no application backend or file-upload endpoint. The site is static files delivered by a web server or CDN, which is what serves the HTML, CSS and JavaScript you are reading. Nothing on the other side of that connection can receive an archive: no endpoint exists that accepts one.
  • The browser blocks it. This page ships default-src 'none' with connect-src 'self': no third-party origin can be contacted at all, and the browser enforces that, not us.
  • The analysis code contains no network call. No fetch, no XMLHttpRequest, no WebSocket, no sendBeacon. An automated test asserts their absence on every run.
  • Nothing persists by default. An ordinary analysis lives in memory and is gone when you reload. Saving is a separate, explicit action.

Open your browser's developer tools, switch to the Network tab, and analyse a file. The only request is Studio loading its own worker script.

What the statuses mean

StatusMeaningWhat established it
VerifiedThese are the original bytes. The entry was read, decompressed if needed, and the recomputed CRC-32 matched the stored value.
Structurally validConsistent, but contents unproven. Headers agree and the data lies inside the file, but the CRC could not be recomputed.
Potentially recoverableData was found that may be recoverable. A local header and a plausible data range exist; the index does not describe the entry and its content is unproven.
DamagedA contradiction was confirmed. A CRC mismatch, a range past the end of the file, or fields that disagree.
UnknownNot enough evidence either way. Encrypted, an undecodable codec, or the analysis was stopped.

These are evidence statuses. Extraction carries a separate operation status, so an extracted entry never silently becomes a verified one — and a failed extraction never makes a verified entry stop being verified. The two axes answer different questions: what the archive proves, and what you asked Studio to do.

Download individually verified files

Select one entry that is already Verified and Studio will read it back out of the archive, decompress it if it is compressed, recompute its CRC-32 over exactly the bytes it is about to hand you, and offer a download only if that checksum matches the value the archive records. Available only when VERAQIS can revalidate the extracted output.

  • One entry, one explicit action. Selecting a row does nothing on its own. There is no extract-all, no automatic extraction and no rebuilt archive.
  • The source archive is never changed. The browser opens it read-only; Studio has no write path to it. The download is a new file.
  • Potentially recoverable entries are not extracted in this release. Neither are structurally valid, damaged or unknown entries — if the checksum has not been recomputed and matched, there is nothing to revalidate against.
  • Encrypted entries are refused. No password is guessed, derived, stored or requested.
  • Stored and Deflate only. Deflate uses the browser's own decoder, checked against a known-answer test first. No decompression library is loaded from anywhere.
  • The download name is not the archive path. A single file is saved as one file, so ../../etc/passwd is saved as passwd — and Studio tells you that it changed the name and why.
  • Nothing partial is ever offered. Cancel, a size mismatch, a checksum mismatch or a crash all discard the bytes produced so far.
  • A matching CRC-32 is not proof of authorship. It shows the extracted bytes are the bytes the archive recorded. It is not a cryptographic authenticity guarantee, and we built the collisions that prove the difference.

What Studio does not do

  • It does not repair or rewrite anything. It analyses, and it can hand you one verified file at a time. Rebuilt archives, multi-file export and any form of speculative recovery are later phases, each gated on its own measured benchmark.
  • It never modifies your file. The archive is opened read-only by the browser; Studio has no write path to it at all. Extraction produces a new download and leaves the archive byte-for-byte as it found it.
  • Encrypted entries stay unknown. Encryption is detected and reported. Nothing guesses, derives or requests a password.
  • Only Stored and Deflate get a checksum check. BZIP2, LZMA, Zstandard and PPMd entries are described structurally and reported unverified — never assumed intact.
  • Nested archives are detected, not opened. Recursive expansion is never automatic.
  • A matching CRC-32 is not a signature. It is strong evidence against accidental damage and none at all against deliberate modification — we built the collisions that prove it.
  • It works offline once the page has loaded, because no application backend was ever in the loop.

Browser support

Studio needs module Web Workers and, for compressed entries, DecompressionStream('deflate-raw'). Saving projects needs IndexedDB; offline use needs Service Workers. Where a feature is missing, Studio disables that control and says why — it never reports an unverified entry as verified because a checksum could not be computed.

Chrome, Edge and Firefox are verified in this release. Safari is expected to support the required APIs but has not yet been verified by the VERAQIS test suite. That is a gap in our evidence, not a claim about Safari: we do not mark a browser as supported on the strength of a compatibility table.

The File System Access API is not required: Firefox does not implement it, so exports fall back to ordinary downloads and no capability is lost.
