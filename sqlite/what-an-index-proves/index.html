What an index proves when the table is gone

Every index in a database is a second, partial copy of the data, written at a different time to a different place. When the table it belongs to is destroyed, that copy is suddenly the most valuable thing in the file — and the most dangerous, because it is almost a backup of the rows. This measurement is about how much an index genuinely proves, and about the discipline needed to stop it being read as more.

Published 4 September 2026 · EXP-SQL-015 · VERAQIS 0.2.1

What is actually in an index

An index b-tree stores one record per row: the columns being indexed, followed by the key of the table row they belong to. Nothing else. For a table of messages indexed on a timestamp, the whole index is five pairs:

CREATE INDEX idx_messages_ts ON messages(ts);

  4500|5   4600|4   4700|3   4800|2   4900|1

  each entry proves:  a row with rowid 5 existed, and its ts was 4500
  each entry says about the body column:  nothing whatsoever

That distinction is the whole subject. The index is genuine, independent evidence about existence and about the indexed columns — and it is silent about every other column in the row. A recovery tool that blurs the two produces something far worse than a gap: a row that looks recovered and is mostly invented.

This is why index findings are reported in their own section and never enter the recovered-rows list. Not as a presentation choice — as a containment rule. A value that reached the report through the index can never be mistaken for a value that came out of the table.

The result that matters

The test is the case where the index is all that is left. The table's leaf page was emptied, so the row data is genuinely gone; the index was left intact.

With the table b-tree yielding nothing, the index still proved that all five rows existed and what each of their timestamps was, and still refused to supply their contents. That is complete recall of existence with zero recall of content — and the report says so explicitly rather than presenting five partial rows.

The undamaged direction is checked too, and it is the more common one in practice: when the table is readable, the index becomes corroboration. All five entries matched rows the table b-tree had already produced independently, which is a second witness to the same fact rather than a new one.

Two fixtures, deliberately mirrored. The second asserts a claim the gates can falsify: the table gives nothing, the index gives existence, and the payload column stays empty. A dash and a zero are kept distinct throughout — "this fixture does not exercise that claim" is not the same fact as "it exercised it and found none".

The rule is enforced rather than intended. Every index entry reports its content as not reached, corroborated or not; no index entry can populate a row's values; and the property is asserted under fuzzing — 4,000 mutated inputs in the in-repo sweep plus a continuous target — with a check that no input can make an entry claim a payload.

Two ways to read an index wrongly

Index pages look enough like table pages to invite reusing the table code on them. Both differences below are silent when got wrong — no error, no malformed structure, just quietly incorrect output.

1. The overflow threshold is a different formula

A record too large for its page spills onto overflow pages, and the size at which that happens is computed differently for index pages than for table leaves. The constants are close enough to be mistaken for each other.

page kindthreshold formulaat a 4096-byte page
table leafX = U − 354061 bytes
index pageX = ((U − 12) × 64 / 255) − 231002 bytes
a nearby constant that is not this oneM = ((U − 12) × 32 / 255) − 2364 versus 32 — the easy mistake

Proven rather than assumed: a 1,500-byte key spills under the index rule and would not under the table rule. Using the table formula on an index would mis-classify which records spill and silently truncate keys — producing shorter values that still look like values.

2. The rowid is not where a table cell keeps it

A table-leaf cell is [length][rowid][payload]. An index leaf cell is [length][payload] — no rowid varint at all. The row key is instead the last column of the record, because an index key is "the indexed columns followed by the key of the corresponding table row".

And that trailing column is a rowid only for rowid tables. For a WITHOUT ROWID table the index b-tree is the table, and its last column is ordinary data. Reading it as a rowid would fabricate row identities — on exactly the kind of table that already needs special handling. So a rowid is extracted only when the indexed table was independently confirmed to be a rowid table, decided from the root page's type byte rather than from what the schema text calls it.

That last clause is the same decision, made in the same place, as the one behind the tables our recovery looked past — the byte on the page is the fact, the schema text is the description. Getting it right once fixed a missing table; getting it right here prevented inventing identities.

Why it is not on by default

Reading indexes means a second walk over the b-trees, and it is not free: +18.0% on the fixture, 14.2 to 16.8 microseconds. The standing rule is that the default path does not pay for capability most runs will not use, so index evidence is requested explicitly. Its cost is measured and reported separately rather than folded into the headline.

Limits

  • An index can never return a row. Existence and the indexed columns are the ceiling; nothing else in the record is in the index to recover.
  • Index keys that spill onto overflow pages are skipped and counted, not decoded from the fragment that fits on the page. An abstention, recorded.
  • Corroboration is not independence in every sense. An index entry confirms a row the table produced, which is a real second witness — but both live in the same file, so neither is evidence against the file having been altered as a whole.

Questions about index evidence

Can a SQLite index be used to recover deleted or lost rows?

It can prove that a row existed and what its indexed columns contained — nothing more. On a fixture with the table emptied, the index proved all five rows had existed and gave their timestamps, and supplied no other column. An index holds only the indexed columns plus the row key, so the rest of the row is not there to recover.

What is stored in a SQLite index b-tree?

One record per row, made of the columns being indexed followed by the key of the corresponding table row. For an index on a timestamp column, each entry is a timestamp and a rowid. There is no copy of the other columns anywhere in the index.

Is an index entry independent evidence that a row existed?

Yes, in the useful sense: it is written separately from the table b-tree, so when both agree they corroborate each other. It is not independent in the stronger sense — both live in the same file, so an index cannot testify that the file as a whole was not altered.

Why do index pages need different parsing from table pages?

Two differences that are silent when got wrong. The overflow threshold uses a different formula, so the table rule applied to an index mis-classifies which records spill and truncates keys. And an index cell has no rowid varint — the row key is the last column of the record instead.

Does the last column of an index entry always give the rowid?

No. For a WITHOUT ROWID table the index b-tree is the table itself and the trailing column is ordinary data. Reading it as a rowid would invent row identities, so it is only treated as one when the indexed table has been independently confirmed to be a rowid table from its root page type byte.
