Experiment EXP-SQL-016

The table our own recovery looked straight past

A recovery tool returning nothing for a table is bad. A recovery tool returning nothing for a table and reporting success is worse, because the output looks complete. That is what ours did for every table declared WITHOUT ROWID: zero rows, no error, a clean run. The cause was one byte, the fix was a routing change, and the reason it survived so long is the interesting part.

Published 4 September 2026 · EXP-SQL-016 · VERAQIS 0.2.1

Two kinds of table

An ordinary SQLite table is a b-tree keyed by a hidden 64-bit integer, the rowid. Add WITHOUT ROWID to the CREATE TABLE and that changes completely: the table becomes a b-tree keyed by its own primary key, and — this is the part that matters for recovery — it is stored as an index b-tree, not a table b-tree.

The distinction is visible in exactly one place: the first byte of each page. A table leaf is 0x0D. An index leaf is 0x0A. Everything else about the page — the cell pointer array, the payload, the record header with its serial types — is read the same way.

CREATE TABLE kv(k TEXT PRIMARY KEY, v TEXT) WITHOUT ROWID;

  root page 2, first byte 0x0A          <- an index leaf
  the schema says  type = "table"       <- and it is a table

  the table walker looked for 0x0D
  the root was 0x0A
  so nothing looked

The code that collected table pages searched for 0x0D. A WITHOUT ROWID table's root is 0x0A. The search found no pages, so no cells were parsed, so no rows were emitted — and because finding zero pages is a perfectly normal outcome for a table that is genuinely empty, nothing anywhere reported a problem.

A table declared WITHOUT ROWID returned 0 of its 4 rows, with no error raised and no warning in the report. The failure was indistinguishable from an empty table, because at the level the code was working, an empty table is exactly what it looked like.

EXP-SQL-016 / gap G-10 · fixture SQL_GT_007, CREATE TABLE kv(k TEXT PRIMARY KEY, v TEXT) WITHOUT ROWID, root page 2, type byte 0x0A

The rows were never damaged

Before writing any code, the first cell of that table was decoded by hand. This matters: it settles whether the problem is that the data is hard to read, or that nobody read it.

first cell of SQL_GT_007, decoded by hand

  15            payload length = 21
  03            record header length = 3
  1d 21         serial 29 -> TEXT(8), serial 33 -> TEXT(10)
  "KEY-0001" "VAL-000001"

  03 1d 21 | "KEY-0001" "VAL-000001"
  ^header    ^both columns, and no trailing rowid

A complete, undamaged record — both columns present, and no rowid at the end because this table has none. Every component needed to read it already existed in the engine: the index-page collector built for a previous experiment, the record parser, the overflow follower, the evidence axes. The gap was routing, not decoding.

So the fix is one decision moved to the right place: choose the walker by the root page's type byte rather than by what the schema calls the object. A schema entry declaring type="table" over an index b-tree is routed to the WITHOUT ROWID path, because the byte on the page is the fact and the schema text is the description.

After routing by the root page type byte, the fixture recovers exactly 4 rows whose key and value equal the independently authored ground truth, with 0 false positives — recall 1.000. Recovered rows carry no rowid, because the table has none, and no synthetic rowid is invented to fill the column.

Why this survived so long

Three properties combined to keep it invisible, and each one generalises past this bug.

The failure had no shape

Zero pages found is a legal answer. There was no exception to catch, no malformed structure to report, no counter that went the wrong way — only an absence, which looks like an empty table.

The schema agreed with the wrong reading

sqlite_master calls it a table, and it is a table. Trusting that description over the bytes on the page is a reasonable-looking decision that happens to be wrong.

Nothing in the corpus used it

Until a fixture declared WITHOUT ROWID, no test could fail. The measurement did not find a broken feature; it found a feature that had never been asked for.

A recovery report that says "0 rows" is not evidence that a table was empty. It is evidence that the tool found no rows, which is a different statement. Anyone evaluating recovery output should check an empty result against a table they know had contents — a bug of this shape produces confident, clean, wrong reports.

What it cost, and what it did not

The reach of this is narrower than it first sounds, and the boundary is worth stating precisely rather than reassuringly.

caseaffected?
Ordinary rowid tablesNo. A different byte, a different walker, unchanged by the fix.
WITHOUT ROWID tablesYes — every row, silently. They are the whole of the impact.
Secondary indexesNo, and deliberately: an index is never a row source. It can prove a row existed and what its indexed columns held, never the rest of the row.
Records spilling to overflow pagesAssembled in full, or abstained on. Never emitted as a partial row.

The second row is the one to weigh: WITHOUT ROWID is a deliberate schema choice, common in key-value tables and in application caches, and rare in casually designed schemas. Where it is used, the loss was total.

The corpus now covers it in both directions: a clean WITHOUT ROWID table and a damaged one. The damaged fixture recovers 2 of its rows and counts the third as malformed rather than guessing at it — the same rule that applies everywhere else.

Limits

  • This is a report about one engine. It measures what ours did, and says nothing about what any other tool does with WITHOUT ROWID tables.
  • Recall 1.000 is on this fixture family, not a general claim about every WITHOUT ROWID schema in the world.
  • Index keys that spill onto overflow pages are skipped and counted, not decoded from their local fragment — an abstention, recorded rather than papered over.
  • The fix changes routing only. No new decoding was added, so it inherits exactly the guarantees the existing record parser already had.

Questions about WITHOUT ROWID tables

What is a WITHOUT ROWID table in SQLite?

A table stored as a b-tree keyed by its own primary key instead of by a hidden rowid. It saves a level of indirection and is common for key-value and lookup tables. For recovery the consequence is structural: the table is stored as an index b-tree, so its pages carry index type bytes rather than table ones.

Why would a recovery tool return no rows from a table that has rows?

Because it looked for the wrong page type. A table leaf page starts with 0x0D and an index leaf with 0x0A; a WITHOUT ROWID table uses the latter. Code that collects pages by searching for 0x0D finds none, and finding none is not an error — an empty table produces the same result.

Do recovered WITHOUT ROWID rows have a rowid?

No, because the table does not have one. The primary key is present as an ordinary column value and the rowid field is left empty. Inventing a synthetic rowid to fill the column would be fabricating an identifier the database never had.

Can an index be used to recover a row?

Only partly, and never as a recovered row. An index can prove that a row existed and what its indexed columns contained. The rest of the row is not in the index, so it cannot be produced — and presenting an index entry as a recovered row would over-claim.

How do I know whether a recovery tool handles these tables?

Give it a database with a WITHOUT ROWID table whose contents you know, and check the row count against the truth. The failure mode here is a clean report with zero rows, so an empty result on a table you know had contents is the signal — there will not be an error message.
