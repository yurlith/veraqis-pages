Experiment EXP-SQL-012

The database that cannot prove it is current

Most database recovery questions are about damage. This one is not. A perfectly intact SQLite file, opened by any tool, will hand you rows that look complete and are internally consistent — and may still be missing every change made in the last month. Nothing inside the file says which case you are in. That is the measurement here, and the design consequence: when currency cannot be decided, the honest output says undecidable rather than guessing.

Published 4 September 2026 · EXP-SQL-012 · VERAQIS 0.2.1

The acquisition mistake that leaves no trace

A SQLite database in WAL mode is two files. app.db holds the pages as of the last checkpoint; app.db-wal holds every transaction committed since. A reader that opens both sees the current state. A reader given only the first sees the state as of the checkpoint — which may be seconds old, or months.

The failure mode is that both look identical. There is no error, no warning, no missing-file marker. The database opens, the schema is right, the row counts are plausible, and every integrity check passes, because nothing is corrupt. You are simply reading an older version of the truth.

This is the most common acquisition mistake we see in SQLite work, and it is invisible by construction: copying app.db out of a phone backup, a container, or a live directory — without app.db-wal — silently substitutes a checkpoint for the present.

Why the file cannot tell you

It is tempting to assume a database could detect this — surely a WAL-mode file knows whether it had a WAL? It does not, and the reason is precise. When SQLite checkpoints cleanly and closes, the WAL is emptied or removed and the database file becomes the committed state. That is a normal, healthy end state.

So a WAL-mode database with no WAL beside it has two readings, and the bytes are the same in both:

Reading A — nothing is missing

  • The writer checkpointed and shut down cleanly.
  • The WAL was emptied because it had nothing left to hold.
  • This file is the latest committed state.

Reading B — a month is missing

  • The WAL existed and was not copied.
  • It held every transaction since the last checkpoint.
  • This file is a stale snapshot, and reads as a healthy one.

No field in the header distinguishes them. This is not a gap in SQLite; it is what a write-ahead log is. Which means it is not a gap a recovery tool can close either — and a tool that reports "current" here is asserting something it cannot know.

The complete case table

Rather than special-case the WAL question, the engine derives one verdict — is the latest committed state provable from the artifacts I was given? — over every combination of journal mode and supplied companion. The derivation is exhaustive: these are all the cases there are.

Two of the "no" rows are deliberately kept apart. Undecidable means no evidence a companion was omitted and none that it was not. Unreadable means we know companion state existed and cannot read it — decidable, and worse. Collapsing them into one "unknown" would throw away the difference between a doubt and a known loss.

One residual rides along with the rollback-mode "yes" rows, and it is not a hedge for its own sake: the file cannot say whether the writer was using a journal-less mode (OFF or MEMORY) when it stopped. A torn commit in those modes can leave every individual page well formed. So the claim is "the database is the committed state if the writer was not journal-less", and the engine states the condition rather than dropping it.

For a WAL-mode database supplied without its WAL, whether the latest committed state is present is not merely unknown to this tool — it is undecidable from the artifacts. A cleanly checkpointed database and a stale copy are byte-indistinguishable, so no analysis of those bytes can separate them.

What the engine does with that

The verdict is reported before the rows, not buried beside them, because it changes what the rows mean. In the benchmark this is a claim the gates can falsify, not a code path: a WAL-mode database supplied without its WAL must refuse to call its rows current.

The wal_committed_only row is the same mechanism seen from the other side: with the WAL supplied, every one of the four rows comes out of the log rather than the database, and the state is provable. Without it, those four rows are exactly what a reader would silently not see.

Note what the first row does not say. Three rows are recovered and verified — they are physically and structurally valid, and the tool says so. What it withholds is any claim about currency, in either direction. Those rows are not labelled stale, because they might not be. They are labelled not provably current, which is the only true statement available.

Freshness is a property of the artifact set, not of a row. Whether a WAL was supplied is the same fact for every row in the file. A tool that marked individual rows current or stale here would be inventing a distinction the evidence does not support.

What to do about it

  1. Copy the whole set, always. name.db, name.db-wal, name.db-journal and name.db-shm if present. The -shm file is only a cache and can be regenerated, but the other two carry state.
  2. Prefer the application closing the database to copying it live. A clean shutdown checkpoints the WAL, which turns Reading B into Reading A honestly rather than by assumption.
  3. Record what you collected, including the absence of a companion. "There was no -wal" and "I did not copy the -wal" are different facts, and only the collector can tell them apart afterwards.
  4. Distrust any tool that reports a WAL-less database as current. It is not reading a field you missed; there is no such field.

Limits

  • Completeness of acquisition can never be proven from inside. Even with a valid WAL, "the latest committed state in the supplied set" is not the same as "the latest state that ever existed". A newer copy may exist elsewhere, and no analysis of these bytes can exclude it.
  • Freshness here is artifact-set level. The engine does not yet mark individual rows current, historical or superseded from this verdict alone.
  • The derivation is over journal mode and companion presence. It says nothing about whether the companion you supplied belongs to the database you supplied — a separate check.

Questions about WAL files and currency

What happens if you copy a SQLite database without the -wal file?

You get the database as of its last checkpoint. Every transaction committed after that checkpoint lives in the WAL, so it is missing — and nothing signals this. The file opens, the schema is intact and integrity checks pass, because the file is not damaged. It is simply older than you think.

Can a tool tell whether a WAL file was missing?

No, and this is provable rather than a limitation. When SQLite checkpoints cleanly the WAL is emptied and the database file legitimately becomes the committed state. That end state is byte-indistinguishable from a stale copy whose WAL was left behind, so no examination of the database file can separate them.

Is a database missing its WAL corrupted?

No. It is intact and internally consistent. The question it cannot answer is not "am I damaged" but "am I current" — a different axis, and the one that usually matters when a database is being recovered or examined.

What about rollback-journal mode instead of WAL?

In rollback mode the database file is the committed state after a clean commit, so currency is normally provable without any companion. The cases that break it are a journal that is present but undecodable — a transaction may have been in flight — and modes that keep no journal at all, where a torn commit can leave every page well formed.

Which files should be collected for SQLite recovery?

The database plus every companion: -wal, -journal, and -shm if present. The -shm file is a rebuildable cache, but the other two carry state that cannot be reconstructed from the database alone. Recording that a companion did not exist is also worth doing, because absence and non-collection look the same later.
