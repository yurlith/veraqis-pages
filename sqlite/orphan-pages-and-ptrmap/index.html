Experiment EXP-SQL-022

Why we refuse to follow a chain we can see

This is a measurement about not recovering something. When a page has lost its place in the tree, its record may continue onto further pages, and the pointer to them is sitting right there. Following it usually works. "Usually works" is not evidence, so the engine only follows the chain when a second, independent structure confirms who owns those pages — and returns nothing when it cannot.

Published 4 September 2026 · EXP-SQL-022 · VERAQIS 0.2.1

Two things that can go wrong at once

A row too large for one page does not stay on one page. SQLite keeps as much as fits and puts the rest on overflow pages, each holding a pointer to the next — a forward chain, hanging off the end of the record.

Separately, a page can become an orphan: still present in the file, still readable, but no longer reachable from any b-tree because the pointers that led to it are gone. Orphan pages are one of the more productive things to find in a damaged database, since the rows are often intact.

Put the two together and you get the case this measurement is about: an orphan page holding the start of a long record, with a pointer to the rest. The bytes are right there. The question is whether anything justifies believing that pointer.

For a page still connected to its tree, the answer is easy: the tree that led you there is itself the evidence that this page belongs to that row. An orphan page has, by definition, lost exactly that. Its chain pointer is a claim with no independent support — and a stale pointer left over from earlier use looks identical to a live one.

The second witness, when it exists

Some SQLite databases keep a pointer map: a set of pages recording, for every page, what kind it is and which page owns it. It exists so the file can be compacted, and it is written independently of the forward chain. That makes it exactly the witness this case needs — the same link described from the other end.

The forward chain says

  • Page 214 continues onto page 215.
  • Written as part of the record.
  • Survives whether or not it is still true.

The pointer map says

  • Page 215 is an overflow page owned by page 214.
  • Written separately, for a different purpose.
  • Disagrees loudly when the two do not match.

So the rule is narrow and stated in advance: an orphan record's overflow chain is followed only when the pointer map independently confirms ownership. With no pointer map in the database, or with one that contradicts the chain, the row abstains — the bytes are reported as present and the record is not assembled from them.

An orphan page's overflow chain is followed only when the pointer map confirms ownership of each page in it. Where the database has no pointer map, or where the map contradicts the chain, the row abstains rather than assembling a record from an uncorroborated pointer. Recall is taken where the evidence supports it and nowhere else.

What a contradiction does and does not mean

The corroboration result is not a boolean, and flattening it would destroy the distinction the whole design rests on. There are four outcomes, and three of them are not "no".

resultwhat it means
Confirmedthe pointer map names this page as owned by that record — the chain may be followed
Contradictedboth structures exist and disagree about ownership
Unavailablethe database keeps a pointer map, but not one covering this page
Not applicablethis database has no pointer map at all — nothing was expected and nothing is missing

The last two are the ones usually collapsed into "unknown". They are different facts: a database without pointer maps is not withholding anything, while a missing entry in a database that has them is a gap. Reporting both as the same thing would make the report unable to say which.

A contradiction is the interesting one, because the tempting reading is wrong. It does not mean the bytes are fabricated, and it does not make the row invalid.

ptrmap contradiction on an overflow page

  physical evidence     Observed      the bytes are there
  structural evidence   Valid         the page parses
  content evidence      Decoded       the record reads
  corroboration         Contradicted  ownership is disputed

  the row is still reported, with its bytes and its decoded record;
  the only thing that flips is the ownership fact

This is what it means for the evidence axes to be independent. A disputed corroboration sets one fact and erases nothing else — the bytes remain observed, the structure remains valid, the record remains decoded. A design that let one contradicted witness invalidate a row would be discarding evidence it actually has, which is the same failure as over-claiming with the sign reversed.

When the pointer map contradicts the forward chain on an overflow page, the row keeps its bytes, its spans and its decoded record; only the ownership corroboration flips to contradicted. A contradicted witness marks one fact as disputed and never erases the facts other axes established.

Why abstention is the product

It is worth being plain that this decision loses data. There are databases where following an uncorroborated chain would have returned the right record, and this engine returns nothing for them. That is the trade, made deliberately.

What following it would buy

More rows recovered, most of the time, from files where a stale pointer happens to still be correct — and no way for anyone downstream to tell those rows from the corroborated ones.

What abstaining buys

Every assembled record has an independent statement behind its assembly. A gap in the output is a gap in the evidence, which is a fact a reader can act on.

The same reasoning runs through this whole section. A database without its WAL is not called current; an index is not allowed to supply a payload; a hot journal does not let a provable verdict be read as a current one. Each is a place where more output was available and the evidence did not reach.

Limits

  • Most databases have no pointer map. It exists only where automatic vacuuming is enabled, so for many files the orphan overflow case simply abstains and always will.
  • Confirmation is about ownership, not content. The pointer map says which record a page belongs to. It says nothing about whether the bytes on that page are undamaged.
  • Both structures live in the same file. They corroborate each other against accidental damage, not against a file that was altered as a whole.
  • This is a rule, measured on fixtures. It does not estimate how often orphan pages with long records occur in real databases.

Questions about orphan pages and corroboration

What is an orphan page in SQLite?

A page still present and readable in the file, but no longer reachable from any b-tree because the pointers that led to it are gone. Orphan pages often hold intact rows, which makes them valuable in recovery — and unverifiable, because the structure that would vouch for them is what was lost.

What is a SQLite pointer map?

A set of pages that record, for every page in the database, its type and which page owns it. They exist to support automatic vacuuming, and only appear in databases where that is enabled. Because they are written separately from the forward pointers, they can corroborate them.

Why not just follow the overflow pointer on an orphan page?

Because a stale pointer left from earlier use looks exactly like a live one, and the b-tree that would normally vouch for the link is precisely what an orphan page has lost. Following it works most of the time, and "most of the time" cannot be distinguished from "always" in the output.

What happens when the pointer map disagrees with the chain?

The row keeps everything the other evidence established — the bytes are still observed, the structure still valid, the record still decoded — and the ownership fact is marked contradicted. A disputed witness marks one fact as disputed; it does not invalidate the row.

Does this mean less data is recovered?

Yes, in the cases where an uncorroborated pointer happened to be correct. The trade is that every assembled record has an independent statement behind its assembly, and a gap in the output means a gap in the evidence rather than a silent guess.
