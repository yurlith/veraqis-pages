Experiment EXP-SQL-021

The rows in the file were never committed

The previous measurement in this section was about a database that cannot prove it is current. This one is the mirror image, and it is the more dangerous of the two: a database that can prove what its committed state is, while every row you read out of it is a change that was never committed. One rule, applied one step too early, turns that into a confident false claim — and it was caught by checking the fixture before writing the rule rather than after.

Published 4 September 2026 · EXP-SQL-021 · VERAQIS 0.2.1

What a hot journal is

In rollback-journal mode, SQLite writes the old contents of every page it is about to change into a side file before touching the database. If the write completes, the journal is discarded. If the process dies mid-transaction, the journal survives with its header intact — and that is a hot journal: a standing instruction to put the database back the way it was.

The next connection to open the database performs that rollback automatically. Which means the state you get depends entirely on how the file reached you:

Opened by SQLite

  • The hot journal is detected and applied.
  • The half-finished transaction is undone.
  • You see the last committed state.

Read as bytes

  • Nothing is applied — the file is read as it lies.
  • The half-finished transaction is still in the pages.
  • You see values that were never committed.

A recovery tool is firmly in the second column, and deliberately so: it opens the source read-only and never writes to it, which means it can never perform the rollback. So it reads the uncommitted bytes. That is correct behaviour — and it is exactly why what the tool says about those bytes matters so much.

The measurement

The fixture is a database interrupted mid-transaction, with its journal still hot. Two states can be read out of the same set of files, and they do not agree:

SQL_GT_009 — rollback mode, hot journal present

  database_alone_state             1|UNCOMMITTED-VAL-0000
  committed_state_after_rollback   1|ORIGINAL-VALUE-00000

  freshness verdict:  Provable(RolledBackJournal)
  rows actually emitted from the file:  the uncommitted ones

Read the two lines together. The committed state is provable — the journal holds the pre-images, so what the database would look like after a rollback is fully determined. And the row the engine emits, reading the database as it lies, is UNCOMMITTED-VAL-0000, which no transaction ever committed.

The obvious rule is wrong here. "Freshness is provable, therefore the rows are the current committed state" holds for every other provable case, and fails for this one. Applying it would attach a current-state claim to bytes that were explicitly abandoned — the exact class of over-claim this whole programme exists to remove.

With a hot journal the axis inverts: the companion file holds the committed state and the database file holds the uncommitted one. A rule deriving row currency from the freshness verdict alone would label in-flight bytes as current — a false current-state claim, and the exact mirror of reporting a database missing its WAL as up to date.

The fix is to derive currency from the basis of the verdict rather than from the verdict. "Provable" answers can the committed state be established? — a question about the artifact set. What a row needs is a different question: are these bytes that state?

Pre-registered and exhaustive. Three of the four rows are unsurprising, which is what makes the fourth worth writing down: it is the one a reasonable implementer would get wrong by generalising from the others.

Two ways to be wrong about the same question

Put beside the missing-WAL case, the pair covers both directions of the same error. Neither database is damaged; both are read perfectly; and a tool that reports only "recovered N rows" is silent about the difference.

WAL-mode database, no WAL suppliedrollback database, hot journal present
Is the committed state provable?No — undecidableYes — the journal determines it
Are the rows on disk that state?Possibly; nothing can sayNo — they are in-flight bytes
What a row is labelledUnknownUncommitted
The wrong claim to make"current" — nothing supports it"current" — the verdict seems to support it

The second column is the more dangerous one precisely because there is a positive verdict to point at. Over-claiming needs no dishonesty here, only one inference applied at the wrong level.

This is why the engine carries currency as its own axis per row rather than folding it into a single confidence number. A row can be physically observed, structurally valid, fully decoded — and still uncommitted. Collapsing those five facts into one score would have to pick a direction, and any direction it picked would be wrong for some real database.

What to do with a hot journal

  1. Collect the journal, always. Without it, the same database is merely a file with unexplained values in it, and the rollback that would explain them cannot be reconstructed.
  2. Do not "fix" the database by opening it in a tool that writes. That performs the rollback and destroys the in-flight state, which may be the very thing you needed to see — what was being written when the process died.
  3. Treat the two states as two answers, not as one answer and one error. "What was committed" and "what was in flight" are different questions, and a hot journal is the rare case where both are recoverable.
  4. Distrust a tool that reports one number. A row count says nothing about which of the two states it counted.

Limits

  • The engine reads the database as it lies and never applies the journal. It reports what the committed state would be, and separately decodes the journal's page images; it does not rewrite the source to get there.
  • "Provable" is still scoped to the artifacts supplied. As in the WAL case, it means the committed state is determined by what you handed over — not that no newer copy exists elsewhere.
  • A journal whose header is zeroed is not hot, and carries no rollback obligation. PERSIST and TRUNCATE leave such a file behind at every commit, so the presence of a -journal file is not by itself evidence of an interrupted write.
  • One fixture, one damage class. This measures the rule, not the frequency of interrupted transactions in the field.

Questions about journals and committed state

What is a hot journal in SQLite?

A rollback journal left behind by a transaction that never finished, with its header intact. It holds the original contents of every page the transaction was about to change, and it is a standing instruction to put the database back. The next connection that opens the database applies it automatically.

Why does a recovery tool see different data than SQLite does?

Because opening a database with a hot journal performs the rollback, and a recovery tool opens the source read-only and never writes to it. SQLite shows you the last committed state; reading the bytes shows you the interrupted transaction still sitting in the pages.

If the committed state is provable, are the recovered rows current?

Not in this case, and that is the point. A hot journal makes the committed state provable — it is the database after the rollback — while the rows read out of the file are the in-flight ones. Currency has to be derived from the basis of the verdict, not from the fact that a verdict exists.

Should a hot journal be applied before recovery?

Only with a copy, and only deliberately. Applying it writes to the database and discards the in-flight state, which can be exactly what an examination needs to see. Both states are recoverable while the journal is intact; only one survives the rollback.

Does a -journal file always mean an interrupted transaction?

No. In PERSIST and TRUNCATE modes SQLite leaves a journal file behind after every normal commit, with its header zeroed or the file emptied. Such a journal is not hot and carries no rollback obligation, so its presence alone proves nothing about how the database was last written.
