"CRC failed" — one entry's verdict, not the archive's

A CRC error is the one archive failure that tells you something precise: this entry's bytes are not the bytes that were archived. It says nothing about the entry next to it — and blunt "repair" tools are exactly the wrong response, because they hide which is which.

Published 28 July 2026

What the checksum is doing there

7-Zip:      CRC failed in <name>. The file is corrupt
unzip:      bad CRC 1a2b3c4d  (should be 5e6f7a8b)
Python:     BadZipFile: Bad CRC-32 for file '<name>'
File manager: The compressed (zipped) folder is invalid

When an archive is created, each entry gets a CRC-32 of its uncompressed contents stored alongside it. When you extract, the tool decompresses the entry and recomputes that value. A mismatch means the bytes changed between then and now.

That is a genuinely strong statement. A random corruption has roughly a one-in-four-billion chance of landing on a value that still matches, so a CRC error is close to certain evidence that something really did change. It is also scoped: the check covers one entry, so it convicts one entry.

ZIP_CRC_001

Checksum mismatch on a single entry. Severity Minor — the archive is structurally fine and one file is damaged.

ZIP_CRC_002

Mismatch on multiple entries. Severity Major — usually points at storage or transfer damage across a range rather than one bad file.

Which of the two you have changes the diagnosis. One failing entry among forty suggests a localised problem. Fifteen failing entries suggests the medium the file lives on, and the right next step is to get the archive off that medium before doing anything else.

What the other entries are worth

This is the part people give up on unnecessarily. A CRC failure on one entry is not contagious. Every other entry has its own checksum and can be checked independently — and either verified or reported damaged, individually.

The closest measurement we have on this exact shape is a gzip stream — labelled as gzip, because carrying a number across formats would be dishonest — with a corrupted member in the middle of a multi-member file:

toolresult

The same logic applies to a ZIP: the damaged entry is dropped and named; the rest are extracted and each one carries its own passing checksum as evidence. What a repair tool must not do here

There is an obvious and tempting move: decompress the failing entry anyway, write out whatever comes back, and report success. The file exists, it has plausible size, it may even open.

It is also unverifiable, and the CRC that was supposed to catch this has just been ignored. Worse, there is a subtler version: reconstruct the entry so that the stored CRC does match, then report "checksum verified". That check proves nothing — a solve that targets a checksum satisfies it by construction. Evidence only counts from a verifier the repair did not aim at.

If a tool reports a CRC-failing entry as recovered, ask what it verified against. "It decompressed", "it opens", and "the checksum matches now" are all satisfiable by a wrong file. See the tautology rule.

What to do

  1. Find out how many entries fail. One is a bad file; many is a bad disk, and the disk is the more urgent problem.
  2. Copy the archive off the medium it is on before anything else, if several entries fail.
  3. Re-download if you can. A CRC error on a downloaded archive is often a bad transfer, and a fresh copy verifies cleanly.
  4. Extract everything that verifies, and treat the failing entries as lost unless you have another copy of them.
  5. Look for another copy of just those files. You rarely need the whole archive again — only the entries that failed.
# which entries fail, and which verify
phx analyze archive.zip

# extract only the verified entries; failures are reported, not patched
phx recover archive.zip --output recovered/

The limit of what a passing CRC proves

Worth knowing even when everything passes. A matching CRC-32 is strong evidence against accidental change and no evidence at all against deliberate change: CRC-32 is linear, so any chosen value can be hit by direct construction.

We built archives that demonstrate this — different contents, identical CRC-32, and gzip -t and unzip -t both report them as healthy. If your question is "did this get corrupted", the checksum answers it. If your question is "could someone have swapped this", it does not, and you need a hash recorded before the damage. Questions about CRC errors

What does "CRC failed" mean when extracting a ZIP?

Each entry stores a CRC-32 of its uncompressed contents, written when the archive was created. If the value recomputed at extraction differs, that entry's bytes changed after the archive was written. It is a verdict on that one entry — the others in the same archive may be perfectly intact.

Can a file with a CRC error be repaired?

Not into a verified file. The checksum tells you the bytes are wrong but not what they should have been, and a CRC-32 constrains at most four bytes. What can be done is recover every other entry with proof, and report the failing one honestly rather than shipping unverifiable output.

Are the other files in the archive still good?

Very likely, and it is checkable rather than a matter of hope: each entry carries its own CRC-32, so each can be verified independently. A failure on one entry says nothing about the entry next to it.

Why do several entries fail at once?

That usually points at the storage or the transfer rather than the archive — a failing drive, a bad cable, a truncated or resumed download. Copy the archive to healthy storage before doing anything else, and prefer re-downloading if the source still exists.

If the CRC passes, is the file definitely correct?

Correct against accidental corruption, yes — a random error has about a one-in-four-billion chance of passing. Against someone who chose the bytes, no: CRC-32 is linear and any target value can be forced by construction. We built collisions that pass gzip -t and unzip -t to demonstrate exactly that.
