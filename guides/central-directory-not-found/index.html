Guide · ZIP_EOCD_001 / ZIP_CD_001

"End of central directory signature not found"

Of all the ways a ZIP can fail, this is the one that looks worst and costs least. Every tool reports the archive as invalid, and in the case we measured every byte of file data was still present and recoverable.

Published 28 July 2026

What the error actually says

You will see one of these, depending on what you used:

unzip:      End-of-central-directory signature not found
Python:     zipfile.BadZipFile: File is not a zip file
PowerShell: End of Central Directory record could not be found
7-Zip:      Cannot open file as archive
Windows:    The compressed (zipped) folder is invalid

All five mean the same thing. A ZIP keeps its index — the central directory — at the end of the file, and finds it through a small record in the last few hundred bytes called the end of central directory, or EOCD. Tools scan backwards from the end of the file looking for that record. If they cannot find it, they stop, because without it they do not know what is in the archive or where.

They do not mean your files are gone. Each entry in a ZIP also carries its own header — the local file header — immediately before its compressed data, repeating the name, the sizes and the CRC-32. The index is a convenience. The archive can be read without it.

How the index gets lost

  • The download or copy stopped early. By far the most common. The index is the last thing written, so it is the first thing an interrupted transfer loses.
  • The file was truncated by a full disk or a device removed mid-write.
  • Something was appended. Mail scanners, upload wrappers and some "download managers" tack bytes onto the end, which pushes the EOCD out of the window tools scan.
  • Real corruption in the last sectors of the storage the file lives on.
  • It was never a ZIP. A renamed file, or an HTML error page saved with a .zip name. Check that first — see diagnosing before repairing.

The libarchive row is the interesting one. It shows the entries were never in doubt — a tool willing to walk forward through the file could see all six. What was missing was the map, and a map can be redrawn from the territory.

What "recovered" is allowed to mean here

Rebuilding an index is guessing about structure. What stops it from being guessing about data is that every ZIP entry carries a CRC-32 of its own uncompressed contents, and that checksum was not used to build the index — it is used to check the result afterwards.

So the sequence is: find the local headers, decompress each entry, then verify each one against the CRC it has been carrying since the day it was written. Entries that verify are reported as verified. Entries that do not are reported as damaged. Nothing in between is invented.

On the benchmark cell for ZIP field damage, that discipline scores 3,243 verified bytes out of 3,243 emitted across 24 cases — precision 1.000 with a 95% confidence interval of 0.999–1.000, and zero false bytes. A modelled stock tool emitted the same 3,243 bytes and got them right, but could prove none of them: correct by luck is not the same result as correct with evidence.

That distinction sounds academic until the archive matters. "These six files are byte-identical to what was archived, and here is the check" is a different statement from "here are six files".

What to do

  1. Work on a copy. Any tool that rewrites the file in place can turn a recoverable archive into an unrecoverable one.
  2. Try re-downloading first if the source still exists. A complete original always beats any reconstruction, and this failure is usually caused by an incomplete transfer.
  3. Compare the size against the source if you can. A file noticeably smaller than expected is truncated, and that tells you the tail is missing rather than scrambled.
  4. Check it is really a ZIP — the first bytes should be PK\x03\x04. A renamed file produces the same error and no amount of repair will help.
  5. Then analyse before repairing. Find out how many entries are present and how many verify. That answer decides whether recovery is worth doing at all, and it costs nothing.
# see what is actually there, without writing anything
phx analyze broken.zip

# rebuild the index and extract only what verifies
phx recover broken.zip --output recovered/

When it will not work

  • If the entries themselves are damaged, rebuilding the index does not help them. You get back the entries that verify, and an honest report on the ones that do not.
  • If the archive is encrypted, it is not opened without the password. Detected, reported, and left alone — no guessing, no brute force.
  • If the file was truncated deeply enough to take entries with it, those entries are gone. See unexpected end of archive.
  • If it is not a ZIP at all, no ZIP tool will ever open it.

Questions about a missing central directory

What does "End of central directory signature not found" mean?

It means the small record at the end of the ZIP that points to the archive index is missing or unreadable. Tools scan backwards from the end of the file to find it, and refuse to continue without it. It says nothing about the compressed files themselves, which sit earlier in the file and are usually intact.

Can a ZIP be opened without its central directory?

Yes. Every entry also carries a local file header immediately before its data, so the archive can be read by scanning forward and the index rebuilt from what is found. In a measured case this recovered 336,414 bytes across 6 members with nothing lost, where Python and PowerShell each extracted 0 files.

Why does Windows say the compressed folder is invalid when the files are clearly inside?

Because Windows, like every other ZIP tool, reads the index at the end of the file before showing you anything. A damaged index makes the whole archive read as invalid even though the compressed entries earlier in the file are untouched and recoverable.

Is recovering the index safe, or does it risk corrupting the file?

Reading is safe as long as the tool does not write to the original. VERAQIS opens the source read-only and writes recovered output to a separate location. Tools that repair in place carry a real risk: a failed in-place repair can destroy what was recoverable.

How do I know the recovered files are correct?

Each ZIP entry stores a CRC-32 of its own uncompressed contents, written when the archive was created. Rebuilding the index does not touch that value, so it works as an independent check on the result: entries that verify are reported verified, entries that do not are reported damaged.
