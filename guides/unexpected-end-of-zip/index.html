"Unexpected end of archive" — what a truncated file still holds

Truncation is the most common archive failure and the least understood one. Nothing in the file is wrong — there is simply less of it than there should be. Everything that finished writing before the cut is byte-exact, and can be proven byte-exact.

Published 28 July 2026

How to recognise it

7-Zip:      Unexpected end of archive
tar:        Unexpected EOF in archive
gzip:       unexpected end of file
Python:     BadZipFile / ReadError: end of file header
unzip:      End-of-central-directory signature not found

The giveaway is the file size. Compare it against the source, the original upload, a directory listing, an email attachment size — anything. If your copy is smaller, you are not looking at corruption. You are looking at an incomplete file, and that is a different and much better problem.

Truncation

The file ends early. Every byte present is the byte that was written. Damage is at the tail, and the boundary is sharp.

Everything before the cut is recoverable and verifiable.

Corruption

Bytes inside the file changed. The file may be the right length, and the damage can be anywhere.

What survives depends on where the damage landed.

This distinction decides everything downstream. With corruption you have to find the damage. With truncation you already know exactly where it is: at the end.

Why the last thing written is the first thing lost

Archive formats put their bookkeeping at the end, because a writer streaming data out does not know the final sizes until it is done. ZIP writes its index last. gzip writes its CRC-32 and length last. tar writes its end-of-archive marker last. xz writes its block Index last.

So truncation removes the part every tool reads first. That is why a file missing its final kilobyte reports as completely invalid while containing megabytes of untouched data.

The practical consequence: the error you see describes the missing bookkeeping, not the missing data. Reading that error as "the archive is destroyed" is the single most expensive misreading in this whole area.

The TAR row is the honest one to look at: 16,384 bytes were lost, and the report says so. Recovery reporting that never mentions loss is not reporting.

The entry that straddles the cut

One entry is always in the worst position: the one that was half-written when the transfer stopped. Its compressed bytes are partly present, its checksum is not.

A tool has two options. It can decompress what it has and hand you a partial file — which will look like a real file, open in some applications, and be wrong in ways you find out later. Or it can say so.

VERAQIS abstains on that entry. It is reported as damaged, not truncated-and-shipped. A half-file that presents itself as a whole one is worse than an absence, because an absence is visible in a way silent wrongness is not.

What to do

  1. Re-download or re-copy if you possibly can. This is the failure where a fresh copy most often just works, and a complete original beats any reconstruction.
  2. Check whether the transfer can be resumed. Many servers support ranged requests; curl -C - or a download manager may complete the file rather than restart it.
  3. Do not delete the truncated copy until you have the replacement. It is still worth something.
  4. If the source is gone, analyse before repairing. How many entries finished before the cut is the number that decides whether recovery is worth doing.
# how much finished writing before the cut?
phx analyze truncated.zip

# extract only the entries that verify
phx recover truncated.zip --output recovered/

Limits

  • Data after the cut does not exist. No tool recovers it; anything claiming to has invented it.
  • Compressed formats differ sharply. bzip2 and threaded xz keep independent per-block checksums and recover cleanly; zstd and lz4 carry no independent verifier and we abstain on them.
  • Solid archives are position-dependent. In a solid 7z, how much survives depends on where the damage landed — measured here.
  • Encrypted archives stay closed regardless of how much of them arrived.

Questions about truncated archives

What does "unexpected end of archive" mean?

The file ends before the archive format says it should. Almost always the transfer or copy stopped early, so the bookkeeping written last — the ZIP index, the gzip checksum, the tar end marker — never arrived. The data written before that point is intact.

Can files be recovered from a truncated archive?

Yes, everything that finished writing before the cut, and it can be verified rather than merely produced. In measured cases this was 336,414 bytes from a truncated ZIP and 2,594,816 of 2,611,200 bytes from a truncated TAR, where the standard tools returned nothing usable.

How do I tell truncation from corruption?

Compare the file size against the source. Smaller means truncated: the bytes present are correct and the loss is at the tail. The same size but failing means bytes inside changed, which is corruption and behaves differently.

Can an interrupted download be resumed instead?

Often, yes, and it is the better answer. Many servers support ranged requests, so curl -C - or a download manager can complete the existing file rather than start over. Keep the partial copy until the replacement is verified.

What happens to the file that was half-written?

Its compressed data is incomplete and its checksum never arrived, so it cannot be verified. VERAQIS reports it as damaged rather than decompressing what is there and presenting a partial file as a whole one.
