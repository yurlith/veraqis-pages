What this check actually does

A ZIP file is a sequence of entries, each preceded by its own local file header, followed by a central directory — an index — and an end-of-central-directory record that says where the index starts. Ordinary tools read the index first and give up if it is missing. This check reads the archive from both directions, which is why it can say something useful about a file that will not open.

  1. Reads the last 64 KiB and looks for the end-of-central-directory signature.
  2. Parses that record: entry count, index offset, index size, comment length, and whether anything follows it.
  3. Detects ZIP64 structures and reports when sizes come from them.
  4. Reads the central directory, if it is present and reachable.
  5. Scans the whole file for local file headers, independently of the index.
  6. Cross-checks each index record against the local header it points at: name, compression method, CRC-32, sizes and offsets must agree.
  7. Checks that every declared data range lies inside the file, and flags ranges that overlap another entry or run past the end.
  8. Flags duplicate names, absolute paths, .. traversal, control characters and NUL bytes in entry names.
  9. Recomputes the CRC-32 of each entry it can decode, and compares it to the stored value.

What each status means

StatusMeaningWhat established it
Verified These are the original bytes. The entry was read, decompressed if needed, and the recomputed CRC-32 matched the stored value.
Structurally valid The entry looks consistent, but its contents were not proven. Headers agree and the data lies inside the file, but the CRC could not be recomputed.
Potentially recoverable Data was found that may be recoverable. Integrity is not established. A local file header and a plausible data range exist, but the index does not describe the entry and its content is unproven.
Damaged A contradiction was confirmed. A CRC mismatch, a range past the end of the file, or fields that disagree with each other.
Unknown Not enough evidence either way. The entry is encrypted, uses a codec this check does not decode, or the analysis was stopped.
"Potentially recoverable" is not "recovered". It means bytes exist where an entry should be and the structure around them is plausible. This page does not extract, repair or rewrite anything. Read how verified recovery works for what turning that into a file actually requires.

How local processing is enforced

"We do not upload your file" is a claim worth checking rather than trusting. On this page it rests on four things you can verify yourself:

  • There is no application backend or file-upload endpoint. The site is static files on a CDN, which is what serves this page. No endpoint exists on the other side of that connection that could receive an archive.
  • The page's security policy blocks it. Every VERAQIS page ships default-src 'none'; this one adds only script-src 'self' 'wasm-unsafe-eval' and connect-src 'self'. That second token permits compiling WebAssembly — the one Rust component described below — and grants nothing else: no eval, no inline script, no origin. No third-party origin can be contacted at all, and the browser enforces that, not us.
  • The analysis code makes no request that carries your file. No fetch, no XMLHttpRequest, no WebSocket, no navigator.sendBeacon anywhere in the analysis core, and an automated test asserts their absence on every run. One same-origin request is possible: a file that does not begin with a ZIP signature makes the browser load this site's own compiled probe, which works out whether the leading bytes are a self-extracting stub or damage. That request downloads code to you and sends nothing.
  • Nothing is stored. No cookies, no localStorage, no IndexedDB. Reloading the page discards the file and the result.

You can confirm it directly: open your browser's developer tools, switch to the Network tab, and analyse a file. The only request that can appear is this site fetching its own probe module, and only for a file whose first bytes are not a ZIP signature. Nothing is sent.

Limits — what this check will not tell you

  • It does not repair anything. No extraction, no rebuilt archive, no modification of your file. Analysis only.
  • Encrypted entries stay unknown. Encryption is detected and reported. Nothing here guesses, derives or bypasses a password.
  • Only Stored and Deflate get a CRC check. BZIP2, LZMA, Zstandard, PPMd and others are described structurally and reported as unverified — never assumed intact.
  • A matching CRC-32 is not a signature. It is strong evidence against accidental damage and no evidence at all against deliberate modification — we built the collisions that prove it.
  • Split and spanned archives are not reassembled. One part is analysed as one file, and the page says so.
  • Very large archives are limited by your browser. Entries above the per-entry CRC ceiling are reported structurally without a checksum check.
  • It runs entirely on your machine, so it works offline once the page has loaded.

If your archive is damaged

The diagnosis tells you which of these applies:

  • The index is gone but the entries are not — end of central directory not found.
  • One entry fails while its neighbours are provably fine — CRC failed.
  • The file was cut short — unexpected end of archive.
  • It may not be corruption at all — five reasons a ZIP will not open.

Common questions

Is my archive uploaded anywhere?

No. The file is read by code running in your own browser tab. There is no application backend, no account and no storage. This page's Content-Security-Policy permits same-origin requests only, and no request this page makes carries any part of your archive — the one that can occur downloads this site's own analysis module to you. Closing or reloading the tab discards everything.

Does this repair my ZIP file?

No. It analyses the archive and reports what it can prove. It never writes to your file, never extracts entries and never produces a repaired archive. Where it finds data that looks recoverable it says so, and says explicitly that recovering it is a separate step this check does not perform.

What does verified mean here?

An entry is marked verified only when its data was read, decompressed where necessary, and the CRC-32 recomputed from those bytes matched the value stored in the archive. If the CRC could not be recomputed — an encrypted entry, or a compression method this check does not decode — the entry is never called verified.

Can it check an archive that will not open at all?

Often, yes — that is the main reason it exists. A ZIP's index sits at the end of the file and is the first thing lost to truncation, but each entry also carries its own local header next to its data. This check scans for those headers, so it can list and often verify entries in an archive no normal tool will open.

Which compression methods can be checked?

Stored (method 0) and Deflate (method 8) can have their CRC-32 recomputed, using the browser's own DecompressionStream. Other methods — BZIP2, LZMA, Zstandard, PPMd and others — are listed with their structure but reported as not verified rather than assumed intact.
