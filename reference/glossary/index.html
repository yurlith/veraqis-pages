Glossary — file damage and recovery

Twenty terms that appear in analysis reports, format specifications and recovery discussions. Each definition says what the thing is and why it matters when a file is damaged — not just what the acronym expands to.

Published 28 July 2026

End of central directory (EOCD)

The final record of a ZIP archive. It tells tools where the central directory starts and how many entries it holds. Tools find it by scanning backwards from the end of the file, so damage to the last few hundred bytes makes the whole archive read as invalid even when every compressed entry is intact.

Central directory

The index at the end of a ZIP listing every entry — name, compression method, CRC-32, sizes, and the offset of the entry's local header. It duplicates information already present next to each entry, which is what makes cross-checking possible.

Local file header (LFH)

The header immediately before each entry's compressed data, carrying the same name, CRC-32 and sizes as the central directory entry. If the index is gone, scanning for local headers reconstructs the archive contents.

Data descriptor

An optional record placed after an entry's compressed data holding the CRC-32 and sizes, used when a writer streams output and does not know them in advance. Its presence is flagged in the entry's general-purpose bit flag.

ZIP64

The extension that lifts ZIP's original 4 GiB and 65,535-entry limits. It is signalled by sentinel values in the classic fields plus an extra field, and by a separate ZIP64 end-of-central-directory record and locator.

Solid archive

An archive that compresses all its files as one continuous stream instead of file by file. It compresses better and couples the files together: damage at one point desynchronises everything after it. Files entirely before the damage remain recoverable.

CRC-32

A 32-bit cyclic redundancy check used by ZIP, GZIP, PNG and others to detect accidental corruption. Strong for that purpose — roughly a 1-in-4-billion chance of a random error passing — and forgeable by direct construction, so it is not evidence of authenticity.

Checksum vs cryptographic hash

A checksum such as CRC-32 detects accidental change cheaply and can be forced to any value on purpose. A cryptographic hash such as SHA-256 is designed to make that infeasible. Both answer "did these bytes change"; only the second answers it against someone who wants a particular answer.

Truncation

The file ends before it should — an interrupted download, a full disk, a copy that stopped. Distinctive because everything present is usually undamaged: the loss is at the tail, not scattered through the file.

Bit rot

Gradual, silent corruption of stored data over time from media decay, controller faults or unnoticed transfer errors. The defining property is that nothing announces it: the file still opens, or it stops opening years after it was written.

Erasure

Damage where the missing bytes are known — which ones are gone, not merely that something is wrong. Erasures are far more recoverable than unknown corruption because a checksum covering the gap can determine the answer instead of merely detecting a problem.

Resynchronisation

Finding a point in a damaged stream where decoding can safely restart. Possible where a format has independent blocks or restart markers, impossible where the decoder carries state continuously — which is why xz and bzip2 salvage past damage and LZMA2 solid folders cannot.

Parity / erasure coding

Redundant data computed in advance so that lost pieces can be reconstructed exactly later. PAR2 files and RAID both work this way. Parity is the only method that makes damage position irrelevant, and it has to exist before the damage.

LZ-coupled stream

A compressed stream where each part depends on earlier decoded output through a sliding window or shared coder state. Corruption anywhere desynchronises everything downstream, and there is no independent way to verify a partial result. zstd, lz4 and LZMA2 solid folders behave this way.

Write-ahead log (WAL)

A SQLite side file holding committed changes not yet folded into the main database. Recovering a SQLite database without reading its WAL loses the most recent committed data, so the WAL is part of the file, not an accessory to it.

Cross-reference table (xref)

A PDF's index of where each object lives in the file. If it is damaged, the objects themselves are usually still present and can be found by scanning, and a working index rebuilt from what is found.

Freelist

Pages a database has marked as reusable after deletion. Their contents may still be readable. VERAQIS excludes freelist pages by default: resurrecting deleted rows is a separate, explicit, risk-marked choice, not something recovery should do quietly.

Magic number / file signature

The first few bytes identifying a format — PK\x03\x04 for ZIP, %PDF- for PDF, \x1f\x8b for GZIP. Checking it answers the surprisingly common question of whether the file is the type its extension claims.

False recovered bytes

Bytes a tool returns as recovered that differ from the original. The metric that matters most and is reported least: a tool returning more data with a few wrong bytes looks better on every other measure while being less useful and more dangerous.

Abstention

Declining to answer. Returning "unknown" for a region that cannot be proven is a correct outcome for a recovery tool, and a far better one than an unlabelled guess.

Common definitions

What is the central directory in a ZIP file?

The index at the end of a ZIP listing every entry with its name, CRC-32, sizes and the offset of its local header. Tools read it to know what is in the archive, which is why damage to it makes an archive with perfectly intact contents read as invalid.

What is a solid archive?

An archive that compresses all its files as one continuous stream rather than separately. It compresses better but couples the files: damage at one point desynchronises everything after it. Files that finish decoding before the damage are still recoverable byte-exact.

What is the difference between a checksum and a hash?

A checksum like CRC-32 detects accidental change cheaply, and can be forced to any chosen value on purpose. A cryptographic hash like SHA-256 is built so that forcing a value is infeasible. Use the first to catch corruption, the second to establish identity.
