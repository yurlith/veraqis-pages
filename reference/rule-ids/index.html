Rule ID reference

Every finding in a VERAQIS analysis report carries a rule ID such as ZIP_EOCD_001. The ID is not a log code — it is the key that ties a corpus fixture, a classifier rule, a health penalty and a recovery ground truth together. This page lists all 87 of them.

Published 28 July 2026

How to read a rule ID

The shape is FORMAT_FIELD_NNN. ZIP_EOCD_001 is a ZIP finding about the end-of-central-directory record, sequence 001. Sequence numbers are stable: ZIP_EOCD_001 means the same thing in every version, so a report from a year ago is still readable.

Four attributes travel with every rule, and together they explain why a report says what it says:

field

The exact structure and field the finding is about — EOCD.cd_offset, LocalFileHeader.crc32. This is what makes a finding checkable rather than an opinion.

category

Structural corruption, missing data, checksum mismatch, and so on. Categories decide which repair strategies are even candidates.

severity

Catastrophic, Major, Minor, Benign. Severity drives the health penalty; it does not by itself decide recoverability.

evidence type

How the finding was established — signature mismatch, offset out of bounds, length overflow, truncation marker, checksum mismatch. This fixes the finding's confidence deterministically instead of by a tuned constant.

Severity is not recoverability. ZIP_EOCD_001 is Catastrophic — every tool will call the archive invalid — and it is also one of the most recoverable findings there is, because the entries themselves are untouched. A catastrophic structural verdict often coexists with intact data.

Coverage

SQLite has its own rule family (SQ_) alongside the container formats listed here, and security findings (SEC_) are raised by the sandbox rather than the format classifiers. The counts above cover the container-format registry that phx analyze fires directly.

Rule counts are not a quality ranking. ZIP has 24 because ZIP has more independently-checkable structures — two headers per entry plus a central index plus an end record. LZ4 has 2 because there is very little in an LZ4 frame that can be independently verified at all, which is exactly why we abstain on it.

Questions about rule IDs

What does ZIP_EOCD_001 mean?

The end-of-central-directory signature is missing or zeroed. The EOCD is the record at the very end of a ZIP that tells every tool where the archive index starts, so losing it makes the whole archive read as invalid — even though the compressed entries earlier in the file are usually untouched and recoverable.

Do these IDs stay the same between versions?

Yes. Rule IDs are stable identifiers shared by the damage corpus, the classifier, the health penalties and the recovery ground truth. A report produced by an older build is still readable against this reference.

Does a Catastrophic severity mean the file is lost?

No. Severity describes how badly the structure is broken, not how much data survives. ZIP_EOCD_001 is Catastrophic and is among the most recoverable findings, because the index can be rebuilt from the entries it was describing.

Where do SEC_ rules come from?

They are raised by the sandbox rather than by a format parser — compression-bomb ratios, overlapping entries, path traversal, symlink and recursion limits. A security finding drives recoverability to none rather than producing a repair plan.
