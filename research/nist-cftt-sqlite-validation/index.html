Experiment VERAQIS-SQL-VAL-001

We ran the federal SQLite forensics specification against our own tool

The US federal Computer Forensics Tool Testing programme publishes a specification for SQLite data recovery: what a tool must report, and how to build the databases that test it. It ships no dataset — each test case describes the commands that create its own fixture. So we built them, ran our own tool against every assertion, and published the result including the cells where we fail.

Published 4 September 2026 · VERAQIS-SQL-VAL-001 · VERAQIS 0.2.1

VERAQIS is not NIST certified, approved, validated or compliant. It was tested internally, by us, using the published CFTT methodology. Only NIST can make a CFTT statement about a tool, and we have not submitted to the programme. Everything below is a self-administered test whose fixtures, harness and results are in the repository.

Why run someone else's specification against yourself

A vendor's own benchmark chooses its own questions, and the questions are where the flattery hides. A published specification written by someone else does not: it asks what it considers necessary, in an order it chose, and a tool either answers or does not.

The CFTT SQLite Data Recovery specification (version 1.0, April 2021) defines 13 core assertions and 8 optional ones — page size, text encoding, journal mode, table and column names, row counts, recoverable rows in the database and in its companion files, the source file each recovered element came from, its byte offset, and whether the source artifacts were altered by the examination.

Against the CFTT SQLite methodology run internally, VERAQIS passes 9 of 13 core assertions on every applicable fixture without a licence, and 11 of 13 with one — the difference being two header fields that a licensed build publishes and an unlicensed build withholds. Both builds recovered byte-identical rows, and all 19 other assertion outcomes were identical between them.

The two core failures are the same failure twice, and it is a design position rather than a bug. VERAQIS recovers history through the transactional record, and not at all through scavenging. Where a no-longer-active row exists in a write-ahead log, it is recovered exactly. Where it exists only as bytes left behind in the free space of the database file, we return nothing.

That choice is deliberate and it is written into the project's own rules: resurrecting deleted content from free space is off by default and gated behind an explicit, risk-marked opt-in, because a row scavenged from unallocated space carries no evidence of when it was live, which table it belonged to, or whether it was ever committed. The specification asks for those rows, and on this methodology the position costs two assertions. We would rather report the cost than change the answer to score better.

The assertion we got wrong first

The specification's journal-mode assertions ask a tool to report how the database handles rollback — WAL, PERSIST, DELETE, OFF. At the first measurement we deviated on it: we published a derived classification instead of the two raw header bytes the specification asks for.

It is a fair thing to be caught by, because the assertion asks for exactly the information a tool is tempted to throw away. The two bytes are read, interpreted into a friendlier label, and then the bytes themselves are gone from the report — which is convenient right up until an examiner needs to say what the file actually contained rather than what a tool concluded about it. We now report both raw header version bytes.

What the specification cannot ask

Passing an assertion grid measures whether a tool answers the questions someone thought to write down. It is worth measuring what falls outside them — so we took a database with a single flipped bit inside a row payload and asked both SQLite and our own analyzer what they made of it.

$ sqlite3 testdata/sqlite/bitflip_payload/SQ_0022.db "PRAGMA integrity_check;"
ok

$ phx analyze testdata/sqlite/bitflip_payload/SQ_0022.db
  health : 100/100 (Perfect)
  no corruptions detected

# for contrast — the same size of damage, on a byte the format constrains:
$ sqlite3 testdata/sqlite/btree_page_corrupt/SQ_0008.db "PRAGMA integrity_check;"
Parse error: database disk image is malformed (11)

$ phx analyze testdata/sqlite/btree_page_corrupt/SQ_0008.db
  health : 65/100 (Significant damage, partial loss)
  MAJOR [structural_corruption] SQ_BTREE_001: page 1: type byte 0xFF not in {2,5,10,13}

A single bit flipped at byte 913, inside a row payload, is reported as intact by SQLite's own integrity check and by our analyzer. The same amount of damage on a page type byte is reported as malformed by both. In this pair the difference is not tool quality: a page type byte has a declared set of legal values, and a payload byte has no checksum, no declared value and no second copy. Elsewhere in the same fixture family it is — see the open gap below.

EXP-SQL-PAYLOAD-EVIDENCE · sqlite3 3.53.2, VERAQIS phx 0.2.1 · fixtures testdata/sqlite/bitflip_payload/SQ_0022.db and testdata/sqlite/btree_page_corrupt/SQ_0008.db · measured 2026-09-04

This is the honest reading of a health score: it is a statement about the evidence the format carries, not about whether the data is right. A score that hedged here would have to hedge on every intact database too, which would make it useless. The same limit binds our recovery claims — content read out of a page like this is bytes as found, and under our evidence model it cannot raise the health of anything.

Where an independent witness does exist — a WAL frame checksum covering that page, a checksum VFS, an external hash manifest — the flip becomes detectable, and detectable by that witness specifically. That is the whole content of the evidence model, arriving from a different direction.

An open gap in the same fixture family

The paragraph above says the two tools agree because the evidence is absent. Checking that across the rest of the family found one file where they do not agree, and where we are the one that is wrong.

$ sqlite3 testdata/sqlite/bitflip_payload/SQ_0050.db "PRAGMA integrity_check;"
*** in database main ***
Tree 4 page 4 cell 2: Rowid 9 out of order
Multiple uses for byte 4062 of page 4
database disk image is malformed

$ phx analyze testdata/sqlite/bitflip_payload/SQ_0050.db
  health : 100/100 (Perfect)
  no corruptions detected
This one is not "nothing to detect". SQLite found structural damage — a rowid out of order, a byte claimed by two cells — with no reference file and no checksum, from the same evidence available to us. Our analyzer missed it. The cause is not established, it is not a calibration threshold, and it is not fixed at the time of writing: it is a detection gap in the structural analyzer, recorded here because finding it while checking our own claim is exactly when it is least convenient and most necessary to say so.

Conclusions this experiment does not support

The source document keeps a list of claims the measurement must not be used for. Publishing it is more useful than publishing another headline, because it is the part a reader cannot check for themselves.

  • That VERAQIS is better than, or outperforms, any other tool. This is a single tool measured against a specification — no comparative run exists, and none is reported here.
  • That VERAQIS is NIST certified, approved, validated or compliant. It has not been submitted to the programme.
  • That passing the source-filename and byte-offset assertions says anything about the quality of our provenance model in general — those assertions ask for a filename and an offset, nothing more.
  • That a 9-of-13 score is a grade. It is the count of assertions answered on this methodology, on six fixtures, by this version.

Limits

  • Six fixtures. That is what the specification defines. It is a methodology, not a large corpus.
  • Two recorded deviations from the literal text: row selection uses a fixed stride rather than a random draw, for reproducibility, and the WAL fixture is captured from inside the open session rather than by killing the process.
  • Our harness was wrong three times before it was right. Each error would have produced a flattering but false result, and each was caught by checking a number that looked too good. The record is in the findings document beside the results.
  • One unresolved detection gap, found while checking the claim above: on SQ_0050 SQLite reports structural corruption and our analyzer reports nothing. Not root-caused, not fixed, and not excluded from this page.

Questions about forensic validation

Is VERAQIS NIST certified?

No. It has not been submitted to the CFTT programme, and only NIST can make a CFTT statement about a tool. What this page reports is an internal run of the published CFTT SQLite methodology against our own tool, with the harness, fixtures and per-assertion results in the repository.

Why does the tool fail the recoverable-rows assertion?

Because it does not scavenge. Rows are recovered through the transactional record — from a write-ahead log, recall was 200 of 200 — and not from freelist or unallocated space, where 111 findable values were returned as zero. A row lifted from free space carries no evidence of when it was live or whether it was ever committed, so resurrecting it is a separate, explicitly risk-marked mode rather than the default.

Can a SQLite database be corrupted without any tool noticing?

Yes, when the damage lands where the format keeps no evidence. A bit flipped inside a row payload leaves the file structurally perfect: SQLite's own integrity check returns ok and our analyzer reports no findings. A bit flipped on a page type byte is caught immediately by both, because that byte has a declared set of legal values.

What does a health score of 100 actually mean?

That nothing detectable is wrong, given the evidence the format carries — not that the data is correct. For formats with checksums the two are close together; for a checksum-less SQLite payload they are not. This is why recovery results carry what each byte was verified against rather than a single confidence number.

Does this show VERAQIS is better than other recovery tools?

No, and that conclusion is explicitly excluded. This is one tool measured against a published specification on six fixtures it built itself. No comparative run exists here, no other tool was run, and an assertion count is not a ranking.

How to cite this

Stable URL, dated, versioned. Quote the numbers with the method attached — every figure above is tied to the experiment that produced it.
