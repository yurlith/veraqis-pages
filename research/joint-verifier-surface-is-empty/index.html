Experiment EXP-0-JMV · negative result

We measured 12 file formats for a recovery engine, then cancelled it

This is a report about work we did not do. Before building a solver that combines several independent checksums to reconstruct lost bytes, we measured whether the opportunity exists at all. Across twelve formats it does not, so the solver was never written — and that is the result worth publishing.

Published 20 July 2026 · Updated 28 July 2026 · EXP-0-JMV · VERAQIS 0.2.1

The idea worth testing

If some bytes of a file are gone but you know which ones are gone, recovery becomes algebra. Each surviving checksum that covers the missing region is a constraint. Enough independent constraints, and the missing bytes have exactly one solution — no guessing, no model, no probability.

One 32-bit CRC gives 32 bits of constraint, which pins down four missing bytes and no more. But formats often carry several checksums. If two or three of them independently covered the same region, you could combine them and solve for much larger gaps. That is a genuinely attractive engine, and it is the kind of thing a recovery vendor would happily announce before checking.

The rule we work under: no recovery solver is built before the size of its addressable surface has been measured. A guessed percentage is never a justification. If the measurement comes back empty, the correct output is a cancelled project and a published number.

Method

For each format we inventoried every checksum that attests payload data, then modelled a known erasure of E bytes. An erasure of E bytes has E × 8 degrees of freedom, so a verifier is sufficient if its width in bits reaches that number.

  • single — one independent verifier is wide enough on its own.
  • joint — no single verifier suffices, but the combined set does, with one verifier held back as an independent confirmer outside the set being solved against.
  • insufficient — neither.

Holding one verifier back is not a formality. A solver that fits a candidate to a checksum will always satisfy that checksum afterwards — the check proves nothing about the answer. Evidence only counts when it comes from a verifier the solver did not target. Without that reservation this experiment would have "succeeded" trivially and dishonestly.

We ran two independence models: a strict one (the honest payload-region model, which is the gate) and a deliberately generous one that counts every data-covering checksum with no region or copy filter. A NO-GO that holds under the generous over-count is robust. Gate: a format is GO only if the joint share reaches τ = 0.10 and the controls come back empty.

Why formats are built this way

The zeros are not an accident of our sample. Checksums in archive formats are designed for error detection, and one checksum per region is exactly enough for that job. Adding a second independent checksum over the same bytes costs space and buys nothing a format designer wanted. Error correction is deliberately left to a separate layer — parity files, RAID, filesystem checksums, recovery records.

The two columns of zeros on the right of the table say something sharper. ISO, SQLite, PDF, TAR, ZSTD and LZ4 carry no independent payload verifier at all. For those formats, byte-level recovery of an erased region cannot be proven by any internal evidence — which is why our work on them is structural and object-level instead: reachability, schema, page and object graphs, rather than arithmetic on bytes.

The single-verifier column is worth reading too. Even where a checksum exists, it only ever pins about four bytes (32 bits) or eight (XZ's CRC-64). That is why the single share tops out at 0.47 for XZ and 0.27 elsewhere: most real erasures are simply wider than any one checksum can determine.

What we did instead

The budget that would have gone into a joint solver went into methods whose surface we had measured and found non-empty:

Prefix salvage

A damaged solid archive is recoverable up to the damage — measured at 87 to 501 of 541 files, zero false files.

Why publish a negative result

Three reasons, in order of how much they matter to someone evaluating recovery software.

  1. It is the honest state of the art. If you are wondering whether some tool can algebraically reconstruct erased bytes from an archive's own checksums, the answer is that the formats do not carry the redundancy for it. That is useful whether or not you ever use our product.
  2. It is a check on us. A vendor that only publishes successes is publishing marketing. The measurement that cancels a project is the one that shows the gates are real.
  3. It saves someone else the work. The measurement harness and its pre-registration are in the repository. If a format ever ships two independent payload checksums, the number moves and the solver becomes worth building.
The rule stands even though the surface is empty: if any future case does combine verifiers, the confirming one must come from outside the set that was solved against. An empty result does not retire the principle.

Questions about format redundancy

Can lost bytes be reconstructed from a file format's own checksums?

Only within the width of a single checksum — about four bytes for a CRC-32, eight for a CRC-64 — and only when you know exactly which bytes are missing. Combining several checksums to solve a wider gap does not work in practice: across twelve formats we measured, every one carries at most one independent checksum over any given payload region.

Which formats carry no payload checksum at all?

Of the twelve measured, ISO, SQLite, PDF, TAR, ZSTD and LZ4 have no independent payload verifier. Recovery in those formats has to be structural — object graphs, schemas, page and directory structure — rather than arithmetic on bytes.

Why does a checksum only pin four bytes?

A 32-bit CRC provides 32 bits of constraint. Four missing bytes are also 32 bits of unknown, so the system has exactly one solution. Five missing bytes are 40 bits of unknown against 32 bits of constraint — 256 candidates, no way to choose, and no honest tool will pick one.

Why publish an experiment that failed?

It did not fail — it returned a clear answer, which is that the opportunity is not there. Publishing it documents the real limits of format-internal redundancy, and it demonstrates that our decision gates cancel projects rather than rationalising them.
