Experiment EXP-HEAD-TO-HEAD

What three ZIP tools recover from the same 1,676 damaged archives

Recovery tools are usually compared by how much they return. That number on its own rewards the wrong behaviour: a tool that writes a plausible file whenever it is unsure will beat a tool that refuses. So we measured both axes at once — how much came back, and how much of what came back was wrong — for three tools on the same 1,676 damaged archives.

Published 4 September 2026 · EXP-HEAD-TO-HEAD · VERAQIS 0.2.1

Two numbers, or the comparison is meaningless

Every archive tool faces the same choice on damaged input: return something, or admit it cannot. Reporting only how much a tool returned scores that choice backwards, because the cheapest way to raise the number is to stop checking. The pair that means something is how much of the recoverable data came back together with how much of what came back was not the original bytes.

The second number is the one that hurts you in practice. A file that is missing announces itself. A file that is present, opens, and contains the wrong bytes does not — it goes into the backup, the case file or the audit, and is found much later or never.

  • Recovered of recoverable — entries returned byte-identical to the original, over the entries the ground truth marks as recoverable from the surviving bytes. A tool is never charged for data the damage genuinely destroyed.
  • False recovery (strict) — produced files whose content is not the original, over every file produced. Strict means an unflagged partial counts as false: half a file presented as a file is a wrong answer.
  • Phantom outputs — files written that no original archive ever contained.

The run

One corpus, one host, one seed, every tool given the same damaged bytes. The corpus is generated from a fixed seed rather than collected, so the ground truth for every entry is known exactly — which is what makes a false-recovery rate measurable at all.

Per damage class — including where we lose

A single headline percentage hides which damage a tool can actually handle. Split by damage class, the three tools do not merely differ in degree — they fail on different things, and two of them fail loudly on classes the third handles.

The nested row is ours to lose. 79.3% against 7-Zip's 100.0% was the one material deficit in this run, and the cause was specific: an archive stored inside another archive carries its own End Of Central Directory record, and when the outer one is destroyed the last such record in the file belongs to the inner archive. The engine anchored on it and read the wrong container.

That was measured first and fixed second. The surface measurement counted 48 affected entries and falsified two candidate fix rules before any code was written — the first would have mis-fired on 294 cases, the second on 142. The rule that survived took the class to 100.0% (116/116), adding 48 entries with none lost and all 48 byte-exact.

Read the competitor columns as of this run. The nested fix and a second change (a directory-derived payload window, +171 entries) were measured on the same corpus and host afterwards, but VERAQIS-only — no competitor binary was re-run for them. The table above is the state where all three tools were measured together, which is the only state in which they are comparable.

Where the gap runs the other way it is large: between-entries 98.1% against 59.4%, insert 96.7% against 50.1%, wrong-size 97.5% against 55.0%, and trunc-head 95.1% against WinRAR's 0.0%. WinRAR's trunc-tail row is worth pausing on — 0.0% recovered, and of what it did produce, 100.0% was not the original content.

Two findings that are not about competitors

A comparison that only produces good news about the tool that ran it is a marketing exercise. Two results here are about us, and neither is flattering.

“Try harder” recovers less

Our best_effort mode reached 84.0% against default's 97.1% — 2,595 fewer entries from the mode a user would reasonably read as the thorough one. The collapse is concentrated in between-entries (43.0% vs 98.1%), insert and wrong-size.

Cause on record: after structural repair the worker marks the directory as reconstructed — correctly, since it no longer carries original bytes — and then refuses entries the original directory could have attested.

We return no partial files at all

7-Zip recovered a true prefix of the original in 19.9% of the 552 partial cases. We recovered 0.0%. Not counted in either headline, but a real capability we do not offer.

This is blocked on a metric decision, not on principle: an unflagged partial is scored as a false recovery, so partials must be emitted and flagged per file — which has to be pre-registered before it is built.

VERAQIS best_effort recovered 84.0% of recoverable entries against 97.1% for default on the same corpus — the mode named for trying harder returns 2,595 fewer entries. It holds false recovery at 0.0%, so the cost is recall, not correctness.

What a single case looks like

The corpus is 1,676 of these. One archive from the crc-mismatch class, analysed by the shipped binary: the stored checksum and the computed one disagree, the rule that fired is named, and the health score reflects one minor finding rather than a verdict on the whole file.

The Expected → Actual column is the whole argument in miniature. The tool is not asserting that the file is fine or ruined; it is showing the two values that disagree and naming the rule that noticed. Everything downstream — the recall number, the false-recovery zero — is built from decisions of this shape.

Limits of this measurement

  • One repetition. Repeatability and the timing distribution are not measured by this run. The timing column is a single sample.
  • A controlled damage matrix, not field failures. The corpus is generated: no encrypted archives, no ZIP64, no non-DEFLATE compression. It measures behaviour on eleven damage classes, not the distribution of damage in the world.
  • ZIP only, one host, one operating system. Nothing here measures 7z or RAR containers, or any other platform.
  • Competitor versions are fixed to the date. 7-Zip 26.01 and RAR 7.22 as of 2026-08-28. A later release may behave differently, and nothing here generalises from a version to a vendor.
  • Competitor rows were not re-run after the two later VERAQIS-only improvements. Comparisons must use the table where all three were measured together.

target/release/recovery-bench --tools veraqis,7zip,winrar --modes default,best_effort \

Questions about comparing recovery tools

Which tool is best for repairing a corrupted ZIP file?

On this corpus, in default mode, VERAQIS returned the most recoverable entries (97.1%) and was the only tool with no wrong files and no invented ones. 7-Zip returned 79.9% with 5.9% of its output not matching the original; WinRAR returned 63.0% with 1.0%. WinRAR's repair mode raises its recall to 91.9% but still produces wrong and invented files. The right tool also depends on damage type — see the per-class table.

What is a false recovery?

A file the tool presents as recovered whose content is not the original bytes. It includes files with wrong content, real entries written out as empty files, unflagged partial files, and files that no archive ever contained. It is measured strictly here: anything produced and not flagged per file counts against the tool.

Why does 7-Zip score well on recall but badly on false recovery?

Because those two behaviours are the same behaviour. 7-Zip decodes what it can and writes the result; that reaches data other readers give up on, and it also writes output when the result cannot be verified. On classes like partial-download it recovers 98.5% and carries a 15.6% strict false-recovery rate at the same time.

Is a benchmark run by the tool vendor trustworthy?

Only as far as it is reproducible and publishes its own bad results. The corpus generator, the seed, the tool versions and the scoring code are all in the repository, and this page publishes the two findings where VERAQIS loses — a mode that recovers less than the default, and a partial-recovery capability we do not have at all.

Does 97.1% mean my damaged ZIP has a 97% chance of being recovered?

No. It is the share of entries that were recoverable from the surviving bytes in this corpus of eleven synthetic damage classes. Your file has one specific kind of damage, and what is recoverable depends entirely on which bytes survived. That is why the analysis is free and reports per entry rather than quoting a rate.

How to cite this

Stable URL, dated, versioned. Quote the numbers with the method attached — every figure above is tied to the experiment that produced it.
