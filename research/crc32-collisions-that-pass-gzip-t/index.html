Experiment EXP-ADV-PCC

A passing CRC-32 does not mean the file is right

Every archive format leans on CRC-32, and almost every recovery tool treats a passing CRC as "the file is correct". We built the counterexample: real archives whose contents differ from the original, whose CRC-32 matches anyway, and which gzip -t and unzip -t declare healthy.

Published 5 July 2026 · Updated 28 July 2026 · EXP-ADV-PCC · VERAQIS 0.2.1

Why this matters for recovery

When a recovery tool repairs a damaged archive and the CRC-32 of the result matches the value stored in the header, the tool declares success. That inference is correct for accidental damage — a random bit flip has roughly a 1-in-4-billion chance of landing on a matching CRC, so a match is strong evidence that the bytes are the original ones.

The inference collapses the moment anyone chose the bytes. CRC-32 is a linear function over GF(2). Given any target value, four bytes of freedom anywhere in the message are enough to hit it exactly. Not "with effort" — by direct construction, instantly.

We are not the first to say CRC-32 is not a cryptographic hash. What we could not find anywhere was the demonstration that matters in practice: a real archive, forged, that the real tools pronounce healthy. So we built it, for five formats.

Result 2 — the same evidence, judged under two threat models

The interesting part is not that CRC-32 is forgeable. It is that the same certificate must be accepted for one purpose and rejected for another — and that a verifier can be built to make that distinction explicit instead of leaving it to the reader.

We ran every forged and honest candidate through two independent verifiers: the shipped Rust re-verifier, and a clean-room Python implementation that shares no code with it. Each was run at accidental grade and at forensic grade.

Both verifiers agreed on every row. Ten cases, five formats. The forged CRC values were, in order: 0xbdb7c46c (zip), 0x14cc3e21 (gzip), 0x1f9d7361 (bzip2), 0x1977ed13 (xz), 0xfbb4d1c7 (png) — each identical to the stored expected CRC of the true content.

Every forged chosen-CRC candidate was accepted at accidental grade and rejected at forensic grade, in all five formats and by both independent verifiers. The discriminator is not a better checksum — it is whether an independent cryptographic witness, created before the repair, confirms the result.

This is why VERAQIS carries an explicit threat model on any claim whose meaning changes between the two, and why an unlabelled result defaults to the weaker reading. A result that does not say which question it answers must not be read as answering the harder one.

The last row is the one people rarely think about. Over-claiming recovery is the obvious dishonesty; over-claiming loss is the other one, and it has real consequences when an insurer or a court is reading the report. Our reference emitter cross-checks every surviving surface before it certifies anything as lost — a naive single-surface emitter would have manufactured a false loss for a region the ground truth knows was recoverable.

What to take from this

CRC-32 is genuinely useful

For accidental damage it is strong, cheap evidence — about 32 bits of it. Our own recovery gates depend on it and that dependency is sound.

It is not identity

A passing CRC-32 never establishes that bytes are the original ones against anyone who could choose them. Neither does a parser opening the file, nor metadata regenerated from the repaired file itself.

The fix is a prior witness

A SHA-256 manifest, a signed parity sidecar, an acquisition hash, or a same-owner source copy — anything cryptographic that existed before the repair.

If you evaluate recovery software: ask what it verified against. "It opens now", "the CRC matches", "the tool reported success" and "the metadata is consistent" are all satisfiable by a wrong file. The only answers that survive an adversary are ones referring to evidence created before the damage.

Limits of this experiment

  • BZIP2 and XZ container-level forgeries were not built (LZ-coupled stream). The region-level CRC test that our per-block salvage actually relies on was tested, and discriminates.
  • This is a statement about CRC-class evidence, not about our accidental-damage benchmark. That benchmark is a non-adversarial ground-truth measurement by pre-registration; the two threat models are kept separate precisely so neither is read into the other.
  • The rejection result is scoped to the patched reference verifiers actually measured here. An older verifier build lacking the positive-coverage rule can accept the overlay/check-divergence forgery — which is why the fix and its provenance are recorded rather than glossed over.

Questions about checksums and integrity

Is CRC-32 enough to verify a file?

For accidental damage, yes — a matching CRC-32 gives roughly 32 bits of evidence that the bytes are unchanged, and a random corruption has about a 1-in-4-billion chance of passing. Against anyone who can choose the bytes, no: CRC-32 is linear, so hitting any target value is a direct construction. We built such collisions for five formats and they pass gzip -t and unzip -t.

Can two different files have the same CRC-32?

Yes, and not just by accident. Because CRC-32 is linear over GF(2), four bytes of freedom anywhere in a message are enough to force any chosen value. In this experiment each forged file differs from the original yet reports the identical stored CRC-32.

What should be used instead of CRC-32?

Nothing needs to replace it for its actual job — detecting accidental corruption cheaply. What is needed in addition, when the question is authenticity rather than corruption, is a cryptographic witness created before the damage: a SHA-256 manifest, a signed parity sidecar, an acquisition hash, or a same-owner source copy.

Does this mean recovery results cannot be trusted?

It means the grade of the claim has to match the grade of the evidence. A CRC-verified recovery is trustworthy as an answer to "was this damaged by accident and did we restore it" and not as an answer to "could someone have substituted this". VERAQIS labels which question a result answers, and defaults to the weaker reading when nothing says otherwise.

Why publish an attack on your own verification?

Because the limit exists whether or not we describe it, and a recovery tool that will not state the boundary of its own evidence is not one worth trusting. The experiment also drove a real fix: a verifier soundness rule requiring a recovered region to be covered by the checks that claim it.
