One bit flip in a solid 7z archive: measuring what actually survives

Conventional wisdom says a solid 7z archive is all-or-nothing: damage anywhere ruins everything. We measured it on a real 541-file archive. The first half of that claim is right and the second half is wrong — and the difference is worth hundreds of files.

Published 25 July 2026 · Updated 28 July 2026 · EXP-7Z-PREFIX-SALVAGE · VERAQIS 0.2.1

The question

A solid archive compresses all its files as one continuous stream, which is why it compresses better than a per-file archive. The cost is coupling: the decompressor carries state — dictionary and range-coder state — from one file into the next. Flip one bit in the middle and everything downstream desynchronises.

That much is documented. What is not documented anywhere we could find is the quantity: given a single bit flip at a known depth, how many files still come out byte-exact? Every answer we found online was qualitative — "the archive is ruined", "try a recovery record". We wanted the number, so we measured it.

Two separate questions fall out of that, and they have opposite answers. We ran both, because a recovery engine must not build a solver for a surface it has not measured first.

Angle A — can the stream heal itself?

Does LZMA2 contain internal restart points a decoder could resynchronise on, recovering data after the flip?

Result: NO-GO. Measured, not assumed.

Angle B — what survives before the flip?

A solid folder decodes sequentially. Are the files entirely before the damage exact, and can we prove each one?

Result: GO. 87 to 501 of 541 files.

Angle A — the stream cannot heal itself

LZMA2 is a chunk stream, and each chunk header declares a reset level: level 0 resets nothing, level 3 resets the dictionary, state and properties. If internal chunks carried a high reset level, a decoder could restart there and recover the tail of a damaged folder.

An earlier measurement counted only dictionary resets. That leaves a gap — a state reset would also be a resync point. So we histogrammed every reset level of every chunk, across three presets (1, 6, 9) and five dictionary sizes (64 KiB to 16 MiB): 15 cells, encoder liblzma (the encoder behind xz, Python lzma and py7zr).

presetdict sizesL0 (no reset)L1L2L3 (full reset)internal resync points
1 / 6 / 964 KiB – 16 MiBall internal chunks000 internal0

All 15 cells behave identically. liblzma emits exactly one level-3 chunk — the first — and every chunk after it is level 0. The range-coder state is carried unbroken across the whole folder.

Across 15 encoder configurations, liblzma emitted zero internal LZMA2 resync points of any reset level. A single bit flip therefore desynchronises the decoder for the entire remainder of the solid folder — there is no restart point to recover on.

This is a negative result and we are publishing it as one. Recovering data after a mid-stream flip in a solid LZMA2 folder is not a hard engineering problem we have yet to solve — it is closed by the format. Any tool that claims otherwise for compressed (non-stored) solid content should be asked which bytes it verified, and against what.

Scope: this covers liblzma. 7-Zip's own encoder was measured separately in an earlier run with the same outcome. RAR's codec is proprietary and stays outside our clean-room boundary — we make no claim about it.

Angle B — everything before the flip is recoverable

"All-or-nothing" quietly assumes the damage kills the prefix too. It does not. A solid folder decodes strictly front-to-back, so every file that finishes decoding before the damaged byte is produced from undamaged input — and each one carries its own CRC-32 in the 7z header, which we can check independently of the decoder that produced it.

So the correct framing is not "solid archives are unrecoverable". It is: a solid archive is recoverable up to the damage, and provably so.

Method

  1. Build a real solid LZMA2 7z archive with py7zr (liblzma, single coder): 541 real files, ~10 MiB unpacked.
  2. Flip a single bit at a fixed fraction of the compressed payload: 20%, 40%, 60%, 80%, 95% — plus an undamaged control.
  3. Run the damaged archive through the shipped CLI (phx recover --semantic 7z), not through a bespoke harness.
  4. Verify every emitted file against its stored CRC-32. A file is emitted only if its CRC verifies; otherwise it is abstained.
  5. Count false_files — emitted files whose bytes differ from the original. The gate requires 0.

The verification step matters more than the recovery step. The CRC-32 used to confirm each file was not targeted by the solver — the solver reconstructs a prefix, then the CRC checks it. That independence is what makes the result evidence rather than a tautology (why that distinction is binding).

The implementation detail that made it work

The obvious approach — decode until the decoder errors and keep what came out — does not work with the decoder we ship. lzma-rs, the pure-Rust LZMA2 decoder in VERAQIS, is all-or-nothing: on a mid-stream error it retains no output at all. We measured that directly rather than assuming it, and it rules out the incremental-flush trick that works with liblzma.

What works with a one-shot API is to make the damaged stream into a shorter valid one. LZMA2 is a chunk stream terminated by a 0x00 byte. Truncate at a chunk boundary before the damage, append 0x00, and you have a well-formed shorter stream that decodes cleanly to the correct prefix. The solver binary-searches for the longest such re-terminated prefix, then CRC-verifies each file inside it.

# recover the provable prefix of a damaged solid 7z folder
phx recover damaged.7z --semantic 7z --output out/

# each emitted file is CRC-verified against the archive header;
# files after the damage are reported, not guessed.

Granularity is one LZMA2 chunk — roughly 2 MiB unpacked. A file straddling the last usable boundary is abstained, not truncated and shipped. Regression on the change: cargo test -p phx_recovery -p phx, 61 passed / 0 failed; the full-decode and non-solid paths were unchanged.

What this does not claim

  • It does not recover data after the flip. That is closed by the format (Angle A) and no amount of engineering changes it.
  • It is not a general 7z repair. Encrypted headers (-mhe=on) and encrypted content are detected and abstained — VERAQIS never guesses, derives or brute-forces a password.
  • The numbers are archive-specific. How many files land before a flip at 60% depends on your file sizes and order. The shape — recovery scales with damage position — is general; the exact counts are not.
  • It says nothing about RAR. RAR's compressed payload uses a proprietary codec we do not decode. That remains a measured NO-GO for us.
  • A passing CRC-32 proves accidental integrity, not authorship. For what CRC-class evidence can and cannot support, see our CRC-32 forgery measurement.

Practical consequence

If you archive with solid compression, damage position is not a detail — it decides your loss. Damage near the end of a solid folder costs almost nothing; damage near the start costs almost everything. If the archive matters, either turn solid mode off for the parts you cannot lose, or add parity so position stops mattering.

And if you are holding a damaged solid 7z right now: it is very likely not a total loss. The correct first step is to find out how much of it is provable, which costs nothing.

Questions about solid archives

Is a damaged solid 7z archive a total loss?

No. Every file that finishes decoding before the damaged byte is recoverable byte-exact and can be verified against its stored CRC-32. In our 541-file measurement, a bit flip at 95% of the payload still left 501 files (92.6%) recoverable, and a flip at 20% still left 87. Data after the damage is not recoverable — LZMA2 has no internal resync point.

Why can data after the flip not be recovered?

Because LZMA2 carries dictionary and range-coder state continuously across the folder. We histogrammed every chunk reset level across 15 encoder configurations and found zero internal resync points, so the decoder never regains synchronisation after a mid-stream corruption.

How do you know the recovered files are correct and not just plausible?

Each recovered file is checked against the CRC-32 stored in the 7z header, and that CRC was not used to construct the candidate — it was used to check it. Files that fail are abstained, never emitted. Across all cells of both measurements, false_files was 0.

Does this work for RAR archives too?

No. RAR compressed payloads use a proprietary codec that VERAQIS does not decode, so RAR payload recovery remains a measured NO-GO for us. VERAQIS can still read RAR5 inventory and extract stored (-m0) files exactly.

Should I stop using solid compression?

Not necessarily — it compresses better. But understand the trade: in a solid archive your loss depends on where damage lands, not just how much there is. For irreplaceable data, either disable solid mode or add a parity sidecar so position stops mattering.
