Experiment EXP-HEAD-TO-HEAD-PHANTOM

Recovering a file that never existed

A recovery tool can fail in a way that is worse than returning nothing: it can hand you a file that never existed. Thirty-nine bytes planted in the right place are enough, and the file that comes out has a name, a size and a checksum that all agree with each other. This is a study of the 220 such files produced during our head-to-head run, and a reproduction you can run in four commands.

Published 4 September 2026 · EXP-HEAD-TO-HEAD-PHANTOM · VERAQIS 0.2.1

What the 447 wrong files actually were

Running three tools over 1,676 damaged archives produced 447 files that were presented as recovered and were not the original data. They fall into four kinds, and the kinds matter more than the total: they fail differently, and they mislead differently.

kindcountwhat the user receives
Phantom220A file no original archive ever contained, written into the output directory with a name and a size.
ContentMismatch86A real entry, written with bytes that are not the original ones.
EmptyPlaceholder85A real entry, whose content was recoverable, written as a zero-length file.
PartialPrefix56The first part of a real entry, presented as the whole file.

From the run's own false-recoveries.json. The EmptyPlaceholder row is the quiet one: the file appears in the listing with the right name, so a directory comparison finds nothing missing.

All 447 of these files were written without a per-file error. In no case did the tool mark the specific file it got wrong, so nothing in the output directory distinguishes the wrong files from the right ones.

That is not the same as claiming the tools were silent. Several of them printed an archive-level error — you will see one below. But an error about the archive does not tell you which of the files it just wrote is the untrustworthy one, and it is the files, not the console, that go into the backup.

Thirty-nine bytes

A ZIP file has two descriptions of its contents. The central directory at the end is the authoritative index. Before it, each entry also carries a local file header — a small record starting with the signature PK\x03\x04 that repeats the name, the sizes and the CRC-32.

When the directory is damaged, every practical tool falls back on scanning the file for those signatures. That fallback is what makes ZIP recoverable at all. It is also the opening: a local file header is only 30 bytes plus a name, nothing in it is signed, and a scanner cannot tell a real one from a planted one by looking at it.

# the 39 bytes: a syntactically perfect header for a file that does not exist
50 4b 03 04    signature  PK\x03\x04
14 00          version needed to extract
00 00          general purpose flags
00 00          method: stored
00 00 00 00    modification time and date
00 00 00 00    CRC-32 of nothing
00 00 00 00    compressed size:   0
00 00 00 00    uncompressed size: 0
09 00          file name length: 9
00 00          extra field length: 0
67 68 6f 73 74 2e 74 78 74    "ghost.txt"

Every field is internally consistent. The declared length is zero, so the checksum of the empty payload is the checksum the header states. A scanner that trusts the signature has no evidence against this record — and no evidence for it either. That distinction is the whole subject of this page.

Reproduce it in four commands

This is the same damage class the corpus generator plants, applied to a two-entry archive small enough to read by hand. The archive is built with fixed timestamps, so the bytes — and the hash below — are identical on any machine.

# 1. build a clean archive (2 entries) and insert the ghost header at the
#    boundary between them. The script is committed: site/scripts/capture-figures.mjs
node site/scripts/capture-figures.mjs

# clean.zip     292 bytes
# ghost header   39 bytes inserted at offset 76
# damaged.zip   331 bytes   sha256 8e4b2dfd...d72d9d67
# 2. extract with 7-Zip
$ 7z x damaged.zip -oout7z -y

7-Zip 26.01 (x64) : Copyright (c) 1999-2026 Igor Pavlov : 2026-04-27

Extracting archive: damaged.zip
ERRORS:
Headers Error

Archives with Errors: 1
Open Errors: 1

$ ls -R out7z
out7z/ghost.txt            0 bytes
out7z/notes/report.txt    30 bytes
out7z/notes/summary.txt   22 bytes

The archive originally held two files. The output directory holds three. 7-Zip did report a problem — Headers Error, exit code 2 — and that report is about the archive as a whole. Nothing marks ghost.txt as the reason, and nothing in the directory it just wrote distinguishes the invented file from the two real ones.

This matters most where a human never sees the console. A backup job, an ingestion pipeline or an e-discovery step reads the directory — and the directory now contains a file that was never in the archive, with a plausible name and a checksum that verifies.

The answer is not refusing — it is saying which

It is tempting to conclude that the correct behaviour is to drop the suspect entry. It is not. The planted header might have been a real entry whose directory record was destroyed — that is exactly what recovery from local headers is for. Discarding it silently is the same failure with the sign flipped: a decision the user cannot see.

So VERAQIS keeps it, and says what it is. Running the container repair over the same file produces a rebuilt archive with all three entries — and a signed manifest that grades each one separately.

# 3. rebuild the container with VERAQIS
$ phx recover damaged.zip --output outphx

recovery: success=true recovered=386B lost=0B strategies=[zip-rebuild]
  health: 15 -> 100
  manifest: outphx\damaged.zip.recovered.phxr.json
  warning: rebuilt central directory for 3 member(s) from local headers
# 4. read the manifest — the entries do not carry equal weight
$ cat outphx/damaged.zip.recovered.phxr.json

"entries": [
  { "path": "notes/report.txt",
    "verdict": "EXACT_RECOVERABLE",
    "existence_evidence": "COMPLETE_CENTRAL_DIRECTORY",
    "content_evidence":   "CRC32_INDEPENDENT",
    "trusted_metric_inclusion": true },

  { "path": "ghost.txt",
    "verdict": "SALVAGED_UNVERIFIED",
    "existence_evidence": "LOCAL_HEADER_SCAN_ONLY",
    "content_evidence":   "CRC32_SELF_CONSISTENT_ONLY",
    "trusted_metric_inclusion": false,
    "abstention_reason": "no complete independent central directory attests that
       this entry belonged to the archive; its checksum proves only that the
       payload matches its own header" },

  { "path": "notes/summary.txt",
    "verdict": "EXACT_RECOVERABLE", ... }
]

CRC32_SELF_CONSISTENT_ONLY is the precise statement of what a planted header proves: the payload matches the checksum in the same record that describes it. A record cannot vouch for itself. The two real entries carry CRC32_INDEPENDENT instead, because a directory record written at a different time and place agrees with them.

Given an archive containing a planted local file header, VERAQIS reproduces all three entries and marks the planted one SALVAGED_UNVERIFIED, excluded from trusted metrics, with the reason recorded in a signed manifest. The invented file is neither passed off as recovered data nor silently discarded.

What the manifest gives you

  • Each entry graded separately, by name.
  • The reason an entry is not trusted, in words.
  • A split between verified and unverified bytes: 0 verified, 386 unverified here.
  • A signature over the record, so the grading cannot be edited afterwards.

What an output directory gives you

  • Three files.
  • No indication which one is which.
  • A console message about the archive, already scrolled past.
  • A checksum that verifies — against a header the same damage could have written.

The other 195 phantoms

The planted-header class accounts for 25 of the 220. The largest group has a different cause and is easier to hit by accident: an archive stored inside another archive.

name writtentimeswhere it came from
inner/data.json71a member of an archive nested inside the damaged one
inner/notes.txt62the same nested archive
inner/level.zip46a further archive nested inside that one
ghost.txt25the planted local file header shown above
a mojibake name14a non-ASCII entry name decoded with the wrong code page
files/item-000_.png2a name whose damaged bytes were repaired into a different name

The inner/… rows are one mechanism: when the outer directory is destroyed, the last End Of Central Directory record in the file can belong to the inner archive, and a reader that anchors on it presents the inner archive's members as the outer archive's contents.

This is not a hypothetical, and it is not only a competitor's problem. The same anchoring mistake cost us the nested damage class in the same run — 79.3% recovered where 7-Zip reached 100.0%. We measured the surface, falsified two candidate fixes against 294 and 142 cases before writing code, and closed the class to 100.0%. The difference in outcome is that anchoring on the wrong archive made us return less, not return files that were never there.

If you are checking output from a repair tool

  1. Count the entries against a listing made before the damage, if one exists. A phantom shows up as a file you cannot account for, not as an error.
  2. Distrust zero-length files in recovered output. Eighty-five of the 447 were real entries flattened to nothing, and an empty file passes most existence checks.
  3. Ask what each file was verified against. "The CRC matched" is only evidence when the checksum comes from somewhere other than the record that describes the file.
  4. Keep the console output with the files. An archive-level error that nobody records is an error that nobody acted on.

Limits

  • The 447 records come from a generated corpus of eleven damage classes, not from field data. They measure how tools behave under those damages, not how often those damages occur.
  • The reproduction above is a single case run on one host with 7-Zip 26.01. It demonstrates a mechanism; the counts come from the full run, not from it.
  • WinRAR could not be included in the live transcript: its ZIP handling lives in a GUI-subsystem binary that writes nothing to standard output. Its figures here come from the benchmark, which captures the files it wrote rather than what it printed.
  • Our zero is a zero on this corpus. It is a measurement, not a guarantee about inputs we have not seen.

Questions about invented files

Can a recovery tool create files that were not in the archive?

Yes. A ZIP entry is announced by a 30-byte local file header that nothing signs, so a scanner recovering from those headers cannot distinguish a real one from one that damage or an attacker planted. Across 1,676 damaged archives, two widely used tools wrote 220 files that no original archive contained.

Why would a damaged archive contain a header for a file that never existed?

Three ways, all measured here: bytes from elsewhere that happen to form the signature, an archive stored inside the damaged one whose own entries get read as the host's, and a deliberately planted header. The last is 39 bytes and every field in it is internally consistent.

Does a matching CRC-32 prove the recovered file is real?

It proves the payload matches the checksum in the record that describes it. If that record is the planted one, the check compares the fake against itself. Evidence requires a second, independent record — in ZIP, the central directory entry written separately from the local header.

Should a recovery tool just refuse anything it cannot verify?

No — that discards real data whose directory record was destroyed, which is precisely what local-header recovery is for. The requirement is that the output says which entries are attested and which are not, in a form that survives into the recovered artifact rather than living in a console message.

How do I tell whether my recovered files are real?

Compare against a listing or hash manifest made before the damage, if you have one. Without one, look at what each entry was verified against: an entry attested by a surviving central directory record is on a different footing from one found by scanning for signatures, and a report that does not draw that distinction cannot help you make it.
