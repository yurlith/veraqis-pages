Format reference

7-Zip — excellent compression, and the recovery bill that comes with it

A solid 7z archive compresses several files as one continuous stream, so a repeated string in file 40 can be encoded as a reference back into file 3. That is why 7z beats ZIP on ratio. It is also why a single flipped bit stops recovery at the damage instead of stepping over it — and why this engine has three rules for 7z and twenty-four for ZIP.

The prefix salvage is a shipped path, not a plan. What it does not do is recover anything after the damage in a solid block, because nothing in the format makes that possible.

Why only three rules

Rule count tracks how much of a format can be checked against itself. A ZIP states every entry twice — once in a local header, once in the central directory — and ends with a record saying where that index begins. Those copies can disagree, and each disagreement is a finding with a name.

A 7z states things once. There is a signature header at the front, one end header at the back describing everything, and between them a compressed stream. There is no second opinion to compare against, so there are three things that can be said: the signature is wrong, the end header is unreachable, or a CRC failed.

Two of those three carry recoverable_hint: false. Only 7Z_MAGIC_001 — a damaged signature over an otherwise intact archive — is marked recoverable, because it is the one fault where the data was never touched.

What a solid block does to damage

We measured this rather than reasoned about it: one bit flipped inside a solid archive, and the question of how much survives.

  • A single bit flip in a solid 7z archive

The finding that matters for recovery is negative and worth stating as such: self-healing past the flip does not work, at any reset level we tried. LZMA2 decoding is all-or-nothing in the library we use, and there is no resync point in a solid folder to restart from. What did work is narrower and real — re-terminating the LZMA2 chunk at a boundary before the damage, which recovers the files stored up to that point and nothing beyond.

That is the honest shape of 7z recovery: a prefix, measured, with no false recoveries — not a repaired archive. A tool promising the files after the damage in a solid block is promising something the encoding does not permit.

Non-solid 7z archives behave differently, and better: each file compressed independently is each file recoverable independently. The ratio is worse. That trade is the whole decision, and it is made at compression time, long before anyone needs to recover anything.

Where the CRCs live, and why it matters

7z does store a CRC-32 per file — in the end header, along with the file names, sizes and the description of how the stream is laid out. So the checksums that would tell you which files survived are in the part of the file most likely to be lost to truncation.

That is what 7Z_TRUNC_001 is: the end header points beyond the end of the file. It is rated Catastrophic not because much data is gone — a 1% truncation can do it — but because losing that header costs the inventory, the checksums and the layout at once. A ZIP truncated the same way loses its index too, but its local headers survive scattered through the file and can be found by scanning. A 7z has no equivalent.

Honest limits

  • The browser check names 7z and declines to read it. Everything here comes from the desktop engine.
  • The bit-flip result is from that experiment and its corpus. It is a strong negative — self-healing did not work at any reset level tested — not a proof that no method could ever exist.
  • Prefix salvage is scoped to LZMA2 solid folders. Other codecs inside a 7z container were not measured.
