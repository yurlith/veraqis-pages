PDF — why a broken document is usually a broken index

A PDF is a bag of numbered objects plus a table saying where each one starts. When a reader says the file is damaged, the table is usually what is damaged — and the table is the one part of a PDF that can be rebuilt from the file itself, because every object announces its own number a few bytes before its content.

PDF and TAR share a blind spot: neither stores a checksum over the bytes it holds. A PDF that opens is not a PDF that is intact.

The same flip, twice

Two rules in the registry describe one bit flipped in two places, and they are rated differently:

rulewhere the bit flippedseverity
PDF_FLIP_001a page content streamMinor
PDF_FLIP_002a cross-reference streamMajor

The damage is identical. What differs is what depends on it. A flip in page content corrupts that page — a glyph, a curve, one image — and nothing else; a PDF has no checksum to notice, so the file opens and the page is quietly wrong. A flip in the cross-reference stream corrupts the map, and a wrong map can make an entire document unopenable while every object in it is perfectly intact.

That is the single most useful thing to know about a damaged PDF: "will not open" and "content destroyed" are almost unrelated conditions, and the first is far more common than the second.

Why the index can be rebuilt

Every indirect object in a PDF is introduced by a line of the form 12 0 obj, and ended by endobj. Those markers are in the file, next to the data, not in the table. So a reader that has lost startxref, or found it pointing at nonsense, can scan the file for object headers and reconstruct the table from what it finds — the same move as recovering a ZIP by scanning for local file headers when the central directory is gone.

%PDF-1.7                        ← PDF_HDR_001 if this is gone
12 0 obj  << /Type /Page … >>   ← the object says its own number
stream … endstream
endobj
…
xref                            ← PDF_XREF_002 if this is gone
0000000017 00000 n              …but the objects above still name themselves
trailer << /Root 1 0 R >>
startxref
   1234                         ← PDF_XREF_001 if this points at nothing
%%EOF                           ← PDF_EOF_001 if this is gone

This is why PDF_XREF_001, PDF_XREF_002 and PDF_EOF_001 are rated Major rather than Catastrophic. They stop every ordinary reader and they destroy nothing. PDF_COMP_001 — a missing xref and a missing object — is Catastrophic, and the difference between the two ratings is exactly whether the thing the index pointed at is still there.

Incremental updates make this more likely to work than it sounds. A PDF edited several times contains several xref sections chained backwards, so an older, intact table often survives further up the file even when the newest one is damaged — at the cost of reverting to an earlier revision of the document.

Truncation, and where the useful part is

Three truncation rules span the range: losing the last 1% is Minor, the last 15% is Major, and half the file is Catastrophic. The gradient is unusual — for most formats truncation is binary, because the index is at the end and losing any of it loses everything.

A PDF degrades instead, because its objects come first and its table comes last. Cut the tail and you lose the map plus whatever objects were in the cut; the objects before it remain individually valid and individually findable. That is the same property that makes the index rebuildable, seen from the other side.

Honest limits

  • Rebuilding an index recovers access, not correctness. A PDF with a reconstructed xref opens; nothing about that says the page content is what the author wrote, because no checksum in the format could tell you.
  • Object streams (/ObjStm) pack many objects into one compressed stream. Damage there behaves like the solid-archive case rather than the scannable one — the objects inside stop announcing themselves individually.
  • Encrypted PDFs are detected and left alone. Nothing here guesses, derives or bypasses a password.
  • The browser check names PDFs and declines to read them. Everything above comes from the desktop engine.
