Format reference

ISO 9660 — everything hinges on sector 16, and there may be a spare tree

An ISO 9660 image begins with 32 KB reserved for a boot sector that is usually empty, and does not identify itself as an ISO until byte 32769. Everything a reader needs — the volume size, the root directory, the path table — hangs off that one sector. Lose it and the image is unrecognisable while every file in it is still exactly where it was.

Sector 16

The first sixteen sectors — 32,768 bytes — are the system area, reserved for boot code and ignored by the filesystem. The primary volume descriptor starts immediately after, and it is the first thing in the file that says "this is an ISO 9660 image". The stamp CD001 sits one byte into it, at 32769, which is exactly why identification reads a 32 KB prefix rather than a handful of bytes.

byte 0      ┌──────────────────────────────┐
            │ system area — 16 sectors     │  usually zeros, or boot code
            │ nothing here identifies the  │
            │ file as an ISO at all        │
byte 32768  ├──────────────────────────────┤
            │ Primary Volume Descriptor    │  "CD001" at 32769
            │  → volume size, root dir,    │  ISO_PVD_001 / ISO_TRUNC_003
            │    path table location       │
            ├──────────────────────────────┤
            │ Supplementary VD (Joliet)    │  a SECOND directory tree
            ├──────────────────────────────┤  ISO_SVD_001
            │ path table, directories,     │
            │ file data — 2048-byte sectors│
            └──────────────────────────────┘

Three rules key on that one sector. ISO_PVD_001 — its magic is gone — is Catastrophic and recoverable: the descriptor is a fixed-layout structure at a known offset, and the data it describes is untouched. ISO_TRUNC_003 — the file is truncated at sector 16 — is Catastrophic and not recoverable, because there the descriptor is not damaged but absent, along with everything after it.

A file that is 700 MB of intact ISO with 32 KB of damage at the front is, to every operating system, not an ISO. The gap between "unmountable" and "lost" is wider for this format than for almost any other.

The spare tree

ISO 9660 restricted filenames severely — uppercase, 8.3, a shallow hierarchy. Joliet works around it by using the format's Supplementary Volume Descriptor to record a separate tree of directory records, in UCS-2, rooted in its own descriptor with its own path table. The point was long Unicode filenames. The side effect is redundancy: a Joliet image describes its contents twice, in two independent structures, pointing at the same file extents.

Cited, not measured here: the Joliet specification and the OSDev ISO 9660 reference. The redundancy is a consequence of the design, not a feature it advertises.

That is why ISO_SVD_001 is one of only two ISO rules marked recoverable. A damaged supplementary descriptor costs the long filenames and nothing else — the primary tree still finds every file. And the reverse holds: a damaged primary tree on a Joliet disc may leave the supplementary one intact, which is a second complete route to the same data.

Redundancy like this is rare among the formats on this site. ZIP repeats each entry's metadata twice and that is the reason its index is rebuildable; ISO with Joliet repeats the entire directory hierarchy. Most other formats describe their contents exactly once.

What ISO cannot see

ISO_SECTOR_001 — a single sector bit flip — is rated Minor, for the same reason TAR_FLIP_001 is: nothing in ISO 9660 verifies file contents. The format was designed for read-only optical media, where error correction lived in the physical layer — CIRC on the disc itself, below the filesystem. Copy that disc to a file on a hard drive and you keep the filesystem and leave the error correction behind.

That is worth stating plainly, because a .iso on a NAS feels like an archive and is not one. ISO_SECTOR_002 — several consecutive sectors zeroed — is Major only because directory records notice; file data zeroed the same way is silent.

Why a rescan works well here

Everything in an ISO is 2048-byte aligned, directory records carry their own length as their first byte, and file extents are addressed as sector numbers. So a reader that has lost the path table can walk sectors, recognise directory records by shape, and rebuild the tree — the same family of move as scanning a ZIP for local headers or a PDF for object markers.

ISO_DIR_001 is the rule for where that breaks: a directory record whose length field is zero. Length zero means "no more records in this sector", so a corrupted length terminates the directory early and hides every entry after it — the records are intact and the walk stops.

Honest limits

  • UDF is a different filesystem and is not covered here. Many .iso files — most DVD and Blu-ray images — are UDF, or both, and this page does not describe them.
  • Nothing here recovers a silently altered sector. As with tar and PDF, the format stores nothing that could detect it.
  • The corpus behind these rules is a sparse clean ISO set; the calibration notes record that as a known limit on what the ISO figures can support.
  • The browser check names ISO images and declines to read them.
