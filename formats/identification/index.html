Format reference

Identifying a file: what its bytes say, and what its name claims

A file extension is metadata a person can type. The bytes are what every program actually reads. When those two disagree — and they disagree constantly — the difference between "this was renamed" and "this is damaged" is the whole diagnosis, and no amount of looking at the name will produce it.

Published 8 August 2026

Two questions, never one

Most tools answer "what is this file?" with a single value, folding the extension in as a fallback when the content is unreadable. That is the right thing to do when the answer feeds recovery: a .zip whose header was destroyed must still be routed to ZIP recovery, or its damage disappears behind a cheerful "unknown file, nothing wrong here".

It is the wrong thing to do when the answer is shown to a person. Folded together, a RAR someone renamed and a ZIP whose first bytes were overwritten produce the same sentence — and they need opposite advice. So the two questions are kept apart everywhere in this project, and reported as a pair.

The entries not at offset 0 are the interesting ones. TAR stamps ustar 257 bytes in, inside its first header block — a TAR has no signature at the very start at all. ISO 9660 puts CD001 at 32769, at its primary volume descriptor, so a disc image cannot be identified from its first sector. And several formats keep their only identity at the end: a fixed-size VHD has no header whatsoever, just a 512-byte footer; a DMG carries its koly trailer there; a Macrium Reflect X image ends with MACRIUM_FILE in its final twelve bytes.

That last group is why identification reads two bounded windows rather than one. A head alone cannot name half the virtual-disk and backup formats on this page — not because they are obscure, but because a head-only table is the wrong shape for them. Neither window scans, so identifying a 500 GB backup image costs exactly what identifying a 3 KB one does.

Order matters and is not alphabetical: the rules are tried in the sequence above, and the first match wins. A file that could satisfy two rules must resolve the same way in every tool that reads this table, which is the reason the order is fixed rather than sorted.

Where these bytes come from

Signature tables circulate widely and are copied far more often than they are checked. So each rule here records how it came to be believed, and the two kinds are never averaged into one confident-looking list: 15 of these 21 formats were measured — the bytes were read off a real file, and the source names which file — while 6 are documented, taken from a vendor specification or a reader implementation and not yet checked here against a real file of that format.

That distinction is not decoration. It reaches the answer: when the checker names a file using a documented rule, it says so on the spot, along with whatever limit the source itself stated — the Acronis rule was verified by its author against True Image 2013 and 2019 and no other builds, and that sentence travels with the result rather than being left in a footnote.

  • VHDX — Microsoft [MS-VHDX], File Type Identifier
  • VHDX and VMDK cross-checked against libyal’s format documentation
  • VMDK — libvmdk, VMware Virtual Disk Format
  • DMG — the UDIF trailer, libmodi
  • Macrium Reflect X — the vendor’s own file-layout repository
  • Acronis True Image — the file(1) magic database submission
Some formats are still absent, and for the same reason stated the same way. Veeam .vbk has no public description of its header that could be cited, so there is no rule for it here. The legacy Macrium .mrimg has no dependable signature — the byte pattern most often quoted for it is a FAT boot sector, which is a property of what the image contains rather than of the format. Guessing either would make this page longer and less trustworthy, which is the wrong trade.

Naming a format is not reading it. The ZIP reference is the only format this browser check opens; for what is provably recoverable from each of the others, the measurements are in the recoverability matrix.

A signature is also not a health check. %PDF- at offset 0 proves the first five bytes survived and nothing else — a file can carry a perfect signature and be unreadable one byte later. Identification narrows the question; it never answers it.
