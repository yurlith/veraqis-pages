Format reference

Identifying a file: what its bytes say, and what its name claims

A file extension is metadata a person can type. The bytes are what every program actually reads. When those two disagree — and they disagree constantly — the difference between "this was renamed" and "this is damaged" is the whole diagnosis, and no amount of looking at the name will produce it.

Published 8 August 2026

Two questions, never one

Most tools answer "what is this file?" with a single value, folding the extension in as a fallback when the content is unreadable. That is the right thing to do when the answer feeds recovery: a .zip whose header was destroyed must still be routed to ZIP recovery, or its damage disappears behind a cheerful "unknown file, nothing wrong here".

It is the wrong thing to do when the answer is shown to a person. Folded together, a RAR someone renamed and a ZIP whose first bytes were overwritten produce the same sentence — and they need opposite advice. So the two questions are kept apart everywhere in this project, and reported as a pair.

Content always wins. A guess taken from a file name is never reported as a fact about the bytes — if the signature is absent, the page and the tool both say so in those words.

The signatures

Each format stamps a fixed byte sequence at a fixed place. Most sit at offset 0; two do not, which is why identification needs a prefix of the file rather than a handful of bytes. The table below is generated from the same rules the tools run, so it cannot drift from them.

The two entries not at offset 0 are the interesting ones. TAR stamps ustar 257 bytes in, inside its first header block — a TAR has no signature at the very start at all. ISO 9660 puts CD001 at 32769, at its primary volume descriptor, which is why a disc image cannot be identified from its first sector.

Order matters and is not alphabetical: the rules are tried in the sequence above, and the first match wins. A file that could satisfy two rules must resolve the same way in every tool that reads this table, which is the reason the order is fixed rather than sorted.

Naming a format is not reading it. The ZIP reference is the only format this browser check opens; for what is provably recoverable from each of the others, the measurements are in the recoverability matrix.

A signature is also not a health check. %PDF- at offset 0 proves the first five bytes survived and nothing else — a file can carry a perfect signature and be unreadable one byte later. Identification narrows the question; it never answers it.

Try it

The browser ZIP check applies exactly this table to whatever you give it. A renamed RAR comes back named, with the mismatch stated; a file named .zip with nothing at the start comes back as a destroyed header rather than as "not a ZIP". Nothing is uploaded — the bytes are read in your own tab.
