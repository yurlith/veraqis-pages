Format reference

gzip and tar — two formats with opposite blind spots, and what happens when you stack them

A plain .tar is one of the easiest damaged archives there is to salvage: every member carries its own header, so a reader that has lost its place can find the next one by scanning. A .gz is one of the hardest: it is a single compressed stream with one checksum at the very end. .tar.gz is the second one wrapped around the first, and the wrapper decides.

The row that matters is the fourth. A tar has no checksum over file contents anywhere in the format — see what tar cannot see below.

Layout — one of these is scannable and one is not

A tar is a flat sequence of 512-byte blocks. Each member begins with a header block naming the file and its length, followed by its content padded to a block boundary. Nothing indexes it: there is no table of contents, and there does not need to be, because every member announces itself.

tar — every member is self-describing
┌──────────────────────────────────────────────────────────────┐
│ header  name, mode, size(octal), checksum, "ustar" @ 257     │
│ data    padded up to a 512-byte boundary                     │
│ header  …the next one, findable by scanning for "ustar"      │
│ data                                                         │
│ 1024 zero bytes  ← end of archive                            │
└──────────────────────────────────────────────────────────────┘

gzip — one stream, one checksum, at the end
┌──────────────────────────────────────────────────────────────┐
│ 1F 8B 08  header (10 bytes + optional name, comment, HCRC)   │
│ ───────────── one continuous DEFLATE stream ───────────────  │
│ CRC32  ISIZE   ← 8 bytes. The only integrity check there is  │
└──────────────────────────────────────────────────────────────┘

That difference is the whole story. Lose a kilobyte from the middle of a .tar and a reader can skip forward, find the next ustar stamp, and carry on: every member after the damage is still recoverable, and you can say exactly which one was hit. Lose a single bit from the middle of a .gz and the DEFLATE decoder loses synchronisation — from that point the output is garbage, and there is no later landmark to recover at.

What tar cannot see

tar has a checksum. It covers the header — the name, the mode, the size — and nothing else. No part of the format verifies the bytes of the file it just stored.

In this engine, TAR_FLIP_001 — a single bit flipped inside a stored file — is classified Minor. That rating is not a judgement about how much your data was damaged. It is a statement about what the format can detect, and the answer is nothing.

undefined

The same blindness covers reordering: TAR_BLOCK_001 (two data blocks swapped) is rated Major only because the resulting sizes stop lining up, not because tar noticed the contents changed. A tar extracted after either of those faults reports complete success, and every tool in the chain agrees with it.

This is why "the archive extracted without errors" is a much weaker statement for a .tar than for a .zip. A ZIP stores a CRC-32 per entry and checks it; a tar has nothing to check. Both will say they are fine.

The checksum tar does have is ambiguous by history

The header checksum is computed by treating the checksum field itself as spaces and summing the header bytes. The standard says unsigned arithmetic — but many early implementations used signed, which changes the result whenever a header contains a byte above 127, as any non-ASCII filename will. The consequence survives to this day: a robust reader computes the sum both ways and accepts the header if either matches.

Sourced from tar(5), not measured here. It matters for recovery because a header that fails one arithmetic and passes the other is a valid header, and a tool that only implements the modern rule will call an intact archive damaged.

What gzip cannot tell you

gzip has the verifier tar lacks: a CRC-32 over the uncompressed data. It has exactly one, in the last eight bytes, and it covers everything. So gzip can tell you the stream is wrong, but only after decompressing all of it, and it can never tell you where — which is the question that decides whether anything is salvageable.

Alongside it sits ISIZE, the uncompressed length — stored modulo 2³². A 5 GB file records its size as 1 GB, and a reader comparing the two disagrees with a healthy archive. That is why GZ_ISIZE_001 is rated Minor here: on a large file a mismatch is expected behaviour of the format rather than evidence of damage.

ISIZE is specified as "the size of the original input data modulo 2^32" in RFC 1952, published in 1996. It is a limitation of the format, not of any implementation.

And a passing CRC-32 is not proof

The single check gzip does carry is strong evidence against accidental damage and no evidence at all against deliberate modification. We built the counterexample rather than asserting it: files whose contents differ from the original, whose CRC-32 matches anyway, and which gzip -t declares healthy.

Stacking them keeps the wrong half

A .tar.gz is a tar compressed as one gzip stream. Every property that makes a tar salvageable — self-describing members, a scannable stamp every few kilobytes, damage confined to the member that took it — exists only in the decompressed bytes. From the outside there is one DEFLATE stream, and damage early in it destroys everything after.

This is the same shape as the finding we measured on solid 7-Zip archives: when a format couples everything into one stream, recovery stops at the damage rather than stepping over it. The remedy is the same too — recover the prefix, and be honest that the rest is gone.
  • A single bit flip in a solid 7z archive
  • Recovering past corruption in xz and bzip2 — where per-block checksums do let you resync

The comparison with xz and bzip2 is the useful one. Both compress in independent blocks with a checksum per block, so a reader can skip a damaged block and resume at the next — measured at 9 of 10 blocks recovered in the headline case. gzip has no such boundary. Nothing about DEFLATE prevents one; gzip simply does not define it.

What to do with a damaged one

  • A plain .tar: treat it as recoverable until proven otherwise. Members after the damage are reachable by scanning for the next header, and a reader that gives up at the first bad block is under-reporting what survived.
  • A .tar.gz truncated at the end: everything up to the cut decompresses normally. This is the common case and the good one — the missing CRC-32 at the end means nothing can be verified, but the recovered prefix is real.
  • A .tar.gz damaged in the middle: expect the prefix and nothing after it. A tool promising full recovery here is promising something the format cannot deliver.
  • Any tar that extracted cleanly: that is not evidence the files are intact. It is evidence that nothing checked them.

Honest limits

  • The browser check on this site does not read gzip or tar. It names them and declines — see identification.
  • The salvage numbers quoted for xz and bzip2 are from that experiment and its corpus, not a universal guarantee. gzip has no equivalent measurement because it has no equivalent mechanism.
  • Nothing here recovers the contents of a tar member that was silently corrupted. No tool can: the information needed to detect it was never stored.
