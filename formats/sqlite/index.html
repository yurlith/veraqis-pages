SQLite — where the integrity checks are, and where they are not

SQLite is the most widely deployed database in the world and it does not checksum its own pages. PRAGMA integrity_check walks the B-trees and confirms they are structurally sound — which is a real and useful check, and is not a check that your rows still say what they said. A flipped bit inside a row passes it.

The same flip, twice

rulewhere the bit flippedseverity
SQ_FLIP_001row data on a leaf pageMinor
SQ_FLIP_002a B-tree interior keyMajor

A flip in row data changes one value and nothing notices — there is no checksum over it, and the B-tree above it is untouched, so every structural check still passes. A flip in an interior key changes the routing: searches take the wrong branch, and rows that are physically present become unreachable. The second is rated worse because more is affected, not because more bytes were damaged.

A SQLite database that passes PRAGMA integrity_check is a database whose structure is consistent. It is not a database whose contents are proven, and the format stores nothing that could make it one.

The checksums are in the write-ahead log

In WAL mode a database is not one file. Alongside db sit db-wal and db-shm, and recently committed transactions live in the WAL until a checkpoint folds them back. Each WAL frame carries a header with a rolling checksum over every prior frame plus itself — so the log is checksummed even though the database it protects is not.

What happens when one of those checksums fails is the part worth knowing: SQLite does not raise an error. It treats the first bad frame as the end of the log and discards it and every frame after it, including frames that are perfectly intact — and the database then passes integrity_check. Committed transactions can disappear without anything reporting a fault.

Cited, not measured here: SQLite does not do checksums and SQLite WAL checksums fail silently and may lose data, with the behaviour discussed on the SQLite forum. This is documented behaviour of a deliberate design, not a bug report — a torn write at the tail of a log is the common case, and truncating there is the safe response. The cost is that a checksum failure earlier in the log looks identical.

Two rules cover this directly. SQ_WAL_001 — a missing WAL header magic — is Minor and the only WAL fault marked recoverable, because a database with an unreadable log is still a valid database at its last checkpoint. SQ_WAL_002, a salt mismatch, is Major: the salt is how a WAL is bound to its database, and a mismatch means the log belongs to a different file or a different generation of it.

Practical consequence for backups: copying db without db-wal copies the database as of its last checkpoint and silently loses everything committed since. This is the most common way a SQLite backup ends up missing data that the application definitely wrote.

Where the format is rigid, and why that helps

Several rules are Catastrophic for reasons that sound trivial. SQ_PGSIZE_001 — page size not a power of two — is one: the page size is read from the header, every offset in the file is a multiple of it, and an impossible value makes the entire file unaddressable. SQ_TRUNC_002, truncated before page 2, is another: page 1 holds the header and the schema, and without the schema the rest is pages of unlabelled cells.

The flip side is that this rigidity makes recovery tractable. Pages are fixed-size and self-typed — the first byte of a page says what kind of B-tree node it is — so a reader can walk the file page by page without trusting any index, identify which pages are intact, and extract the records on them. That is the standard approach to a corrupt SQLite file, and it works because the format repeats its structure everywhere rather than describing it once.

Honest limits

  • The SQLite rules in this engine are declared and classified; the dedicated parser behind them is a later phase. Treat this page as a description of the format and of what the classifier can key on, not as a claim of a shipped SQLite recovery path.
  • Nothing here recovers a row whose bytes were silently altered. As with tar, the information needed to detect it was never stored.
  • The WAL behaviour above is cited from third-party analysis and the SQLite forum, not reproduced in our corpus.
  • The browser check names SQLite databases and declines to read them.
