Formats

File formats

Recoverability is a property of the format, not of the tool. A format that stores an independent checksum per block can be salvaged past damage; one that couples everything into a single stream cannot. These pages map each format to what is actually provable.

Recoverability at a glance

What decides whether damaged data can be recovered with proof is whether the format carries an independent verifier over the region in question — measured, not assumed:

formatindependent payload verifiersalvage past damage?measurement
ZIPCRC-32 per entryyes — other entries verify independentlyZIP reference
7z (solid)CRC-32 per fileprefix only — no resync point exists after the damagebit-flip measurement
xzCRC-32 or CRC-64 per blockyes — 9 of 10 blocks in the headline casesalvage measurement
bzip2CRC-32 per blockyes — reaches the safe optimumsalvage measurement
gzipCRC-32 per membermember-level resyncrule reference
zstd / lz4noneno — we abstainwhy we abstain
PDF / SQLite / TAR / ISOnonestructural recovery only, not byte-level proofjoint-verifier measurement
RARCRC-32 per fileinventory and stored files only — the codec is proprietaryrule reference

The "none" rows are not gaps in our support. They are properties of those formats: there is nothing inside the stream that can independently confirm a recovered region, which is why we report the limit instead of emitting unverifiable bytes.

Practical reading of this table: if you are choosing a format for data you might one day need to recover part of, prefer one with per-block verifiers — xz -T0, bzip2, or a non-solid archive. If you need position-independent recovery, that requires parity added in advance; no format gives it to you for free.
