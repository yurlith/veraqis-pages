ZIP format reference — structure, failure modes, and what is recoverable

Almost every "corrupted ZIP" is one of seven specific failures, and they are not equally bad. Some destroy nothing but the index. This page maps the format to its failure modes, and each failure mode to what can actually be proven afterwards.

Published 28 July 2026

Layout

A ZIP is a sequence of entries followed by an index. Each entry appears twice in the file: once as a local file header immediately before its compressed data, and once as an entry in the central directory at the end. The end of central directory record closes the file and says where that index starts.

┌─────────────────────────────────────────────────────────────┐
│ PK\x03\x04  local file header  #1   name, method, CRC-32,   │
│             compressed data    #1   sizes                   │
│ PK\x03\x04  local file header  #2                            │
│             compressed data    #2                           │
│                    …                                        │
├─────────────────────────────────────────────────────────────┤
│ PK\x01\x02  central directory entry #1  → offset of LFH #1   │
│ PK\x01\x02  central directory entry #2  → offset of LFH #2   │
│                    …                                        │
├─────────────────────────────────────────────────────────────┤
│ PK\x05\x06  end of central directory (EOCD)                  │
│             → where the central directory starts, how many  │
└─────────────────────────────────────────────────────────────┘

Why the index is at the end

ZIP was designed for floppy disks and streaming writers. A writer that does not know in advance how well the data will compress cannot write a correct index first — so ZIP writes entries as it goes and appends the index last. That decision is why you can append to a ZIP cheaply, and also why almost every ZIP disaster looks the same.

The single most important consequence: tools locate the index by scanning backwards from the end of the file. Damage the last few hundred bytes and every tool declares the archive invalid — while the compressed entries, sitting untouched earlier in the file, are perfectly intact. A "totally corrupted" ZIP is very often a ZIP that lost its table of contents.

It also means the deliberate redundancy in the format is useful: name, CRC-32 and sizes exist in both the local header and the central directory. When those two copies disagree, the disagreement itself is evidence — and the actual bytes are the tiebreaker, since a value the data contradicts is never emitted.

What ZIP cannot prove

An honest format page has to include this section, because the limits decide what any tool can legitimately claim.

  • One CRC-32 per entry, and no more. ZIP carries exactly one independent checksum over any given payload region. Combining several to solve for a wider gap does not work — we measured that across twelve formats and the answer was zero everywhere.
  • A CRC-32 pins at most four bytes. With a known erasure, 32 bits of checksum determine 32 bits of unknown. Five missing bytes leave 256 candidates and no way to choose between them.
  • Damaged compressed data is usually gone. DEFLATE is LZ-coupled: corruption inside a compressed stream desynchronises everything after it in that entry. What survives is the other entries, not the damaged one.
  • A passing CRC-32 is accidental-grade evidence. It shows the bytes were not altered by chance. It cannot show they were not altered on purpose — we built the collisions that demonstrate this.
  • Encrypted content stays closed. Detected, reported, abstained. Repairing the unencrypted envelope around an encrypted payload is permitted and never touches the payload.

ZIP is also DOCX, XLSX, APK and EPUB

A .docx, .xlsx, .pptx, .jar, .apk or .epub is a ZIP with a required internal layout. Everything above applies to them — plus a second layer: the package has to be internally consistent, with a content-types declaration and a relationship graph that resolve.

That is why an Office file can be a perfectly valid ZIP and still refuse to open: the container is fine and the package graph is broken. Recovery there means extracting the CRC-verified parts and reporting which relationships are missing — not synthesising the missing parts and calling the document repaired.

Questions about the ZIP format

Why does Windows say a ZIP is invalid when the files are clearly inside it?

ZIP tools read an index at the very end of the file — the central directory, located via the end-of-central-directory record. If that index is damaged or missing, every tool reports the whole archive as invalid, even though the compressed entries earlier in the file are intact. The index can usually be rebuilt from those entries.

Why is the ZIP index stored at the end of the file?

ZIP was designed to be written as a stream, before the writer knows how well each file will compress. Writing entries first and the index last makes that possible, and it makes appending cheap. The cost is that damage to the last few hundred bytes makes the entire archive unreadable to normal tools.

Can every corrupted ZIP be repaired?

No, and the answer depends on which bytes survived. Losing the index usually costs no data. Losing an entry's compressed bytes destroys that entry. Encrypted archives are not opened without the password at all. VERAQIS reports what surviving bytes can prove and marks the rest unknown.

Is a DOCX file really a ZIP?

Yes. DOCX, XLSX, PPTX, JAR, APK and EPUB are all ZIP containers with a required internal layout. They can therefore fail in two independent ways: as a damaged ZIP, or as a valid ZIP whose internal package graph no longer resolves.

What does CRC failed mean when extracting a ZIP?

Each entry stores a CRC-32 of its uncompressed contents. If the value computed at extraction differs, that entry's bytes changed after the archive was written. It is a per-entry verdict: the other entries in the same archive may be perfectly intact and verifiable.
