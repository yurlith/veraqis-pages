Experiments EXP-0-NESTED-ANCHOR and EXP-NESTED-ANCHOR

The end record that belonged to a different archive

A ZIP reader finds the archive by searching backwards for the end-of-central-directory record. That works because there is normally one. Put an archive inside an archive and there are two — and if the outer one is destroyed, the search finds the inner archive’s and reads the file through the wrong lens. This is the measurement of how often that happened to us, and of two plausible fixes that the corpus destroyed before either reached code.

Published 4 September 2026 · EXP-0-NESTED-ANCHOR · VERAQIS 0.2.1

How a reader finds a ZIP

The central directory of a ZIP sits at the end, and the very last thing in the file is a small end-of-central-directory record saying how many entries there are, how large the directory is and where it starts. Every reader begins by scanning backwards for that record's signature.

The assumption underneath is that the last such signature in the file belongs to this file. An embedded archive breaks it: a .zip stored inside another .zip carries its own complete structure, end record included. While the outer record exists it is later in the file and wins. Destroy it, and the backward scan keeps going and lands on an inner archive's.

ci-nested-one-level-nested-outer_cd_removed_inner_clean.zip
file length 82586 · outer central directory and end record removed

  end-record signatures at 27499, 55002, 82564
    all three belong to embedded .zip members

  anchored on 82564:  count=2  cd_size=122  cd_off=19833
  directory relocated to 82564 - 122 = 82442, and real records are there:
    "inner/notes.txt"   local header offset 0
    "inner/data.json"   local header offset 2852

Every value read there is correct — for the inner archive. Those local-header offsets are relative to the embedded archive, which begins at byte 62609 of the outer file. Read as absolute, offset 0 points at the outer archive's first entry and 2852 points into the middle of its payload.

So the engine reported a directory found and two entries seen, listing two names from a different archive, while the six genuine outer local headers — at 0, 7571, 10423, 35083, 62609 and 65461 — were crowded out of the reconciliation.

What stopped this becoming a wrong file on disk was the checksum. Extraction failed on both entries, with a CRC mismatch and a bad local header. That is the last line of defence working, not the first — the reader had already accepted a false description of the archive, and only the byte-level check caught it.

How much of the corpus this reached

Before deciding what to do, the surface was counted: over all 1,676 damaged archives, how many are affected, and is anything actually lost that another configuration recovers?

Eight cases, forty-eight entries, none recovered — and all forty-eight recovered by the same binary in its repair mode, which rebuilds the outer directory from the local headers and gets every entry every time. The trigger is one specific condition rather than a family: the outer directory and its end record are both gone and the archive contains an embedded ZIP.

Across 1,676 damaged archives the mechanism affected exactly 8 cases and 48 entries, none of which were recovered in the default configuration, and all 48 of which the same binary recovered in its repair mode. The data was never unreachable; the reader was anchored on the wrong container.

Two fixes that did not survive the corpus

The obvious fix is to notice that the directory's offsets do not fit the file. Both attempts to turn that into a rule were checked against every case in the corpus before anything was implemented, and both failed the same way — by firing on a completely different kind of damage.

Reject an end record whose rebasing implies the archive starts after byte 0.Inserting bytes at the front of a file shifts every offset and produces exactly the same arithmetic.294 — 181 of them plain insertions where the archive is the only one present and is already handled correctly
…and additionally require undescribed local headers before that start.Inserting bytes before the directory leaves the local headers where they were, so they read as undescribed relative to the shifted start.142 — 53 of them insertions

Neither rule was written into the engine. A fix that recovers 48 entries by mis-handling 294 unrelated cases is not a fix, and the only way to know that in advance is to run the candidate against the corpus rather than against intuition.

That left a genuine blocker rather than a solved problem, and the surface measurement said so: the interaction between the container map and the insertion family was not settled, and settling it was the precondition for any solver. The measurement stopped there deliberately, with no code changed.

Then the feared interaction was measured

The blocker was a concern, not an observation — so instead of designing around it, the engine's own container map was asked directly: across all 1,676 archives, which files anchor on an end record that is precisely a validated embedded archive's own?

…with real local headers in front of that archive38 — all of them

The interaction that blocked the rule did not exist: validation already declines a wholly shifted archive, so no insertion case is flagged at all. The second refinement separates nothing here — 38 of 38 — so it was left out rather than kept as insurance. Unjustified complexity is a cost, not a safety margin.

With that measured, the rule that shipped is one sentence and carries no threshold, no score and no search: when scanning backwards for the end record, skip any candidate whose offset is exactly a validated embedded archive's own end record and keep scanning. If every candidate is foreign, the parse proceeds exactly as it already does when no end record is found at all — by enumerating the outer entries from their local headers.

This is not a heuristic, and the distinction matters. The engine already refuses to promote a nested archive's local headers into outer entries, using the same validated container map. This closes the identical hole for its directory, with the same oracle. Nothing about it estimates or prefers — an offset either is a validated embedded archive's end record or it is not.

Skipping end-record candidates that are a validated embedded archive’s own took the nested damage class from 79.3% to 100.0% of recoverable entries — 116 of 116 — adding 48 entries with none lost and all 48 byte-exact. The rule adds no threshold, no scoring and no search.

What the sequence was worth

The fix is four lines of behaviour. What produced it took three separate measurements, and skipping any of them would have shipped something worse.

Count the surface first

Eight cases and 48 entries — small. Knowing that before starting is what kept the response proportionate instead of a redesign of directory location.

Falsify before coding

Two reasonable rules, 294 and 142 mis-fires. Both would have looked correct on the eight cases they were designed for, and both would have broken a class nobody was thinking about.

Measure the blocker

The interaction that stopped the work turned out not to exist. Designing around a fear would have added a condition that separates nothing — 38 of 38.

Limits

  • A generated corpus of eleven damage classes. It measures behaviour under those damages, not how often archives contain embedded archives in the field.
  • One repetition. Recall is deterministic here; timing and repeatability are not measured by this run.
  • The rule is exact, so its reach is exact. It skips end records belonging to archives the container map validates. An embedded archive too damaged to validate is not recognised, and that case is unchanged.
  • ZIP only. Nothing here transfers to 7z or RAR containers.

Questions about nested archives

Why does a ZIP inside a ZIP break recovery?

Because the inner archive carries its own complete structure, including an end-of-central-directory record. A reader finds the archive by scanning backwards for that signature, so when the outer record is destroyed the scan lands on the inner archive’s and reads the whole file through the wrong container’s index.

What happens when a reader anchors on the wrong archive?

It reports a directory found and lists entries that belong to the embedded archive. The offsets in that directory are relative to the inner archive, so read as absolute they point at unrelated parts of the outer file. Extraction then fails on checksum or header checks — the last line of defence, after the file has already been misread.

How was the problem found?

By counting it. Across 1,676 damaged archives the mechanism affected exactly 8 cases and 48 entries, and the same binary in its repair mode recovered all 48 — which proved the data was reachable and the reader was at fault, before any fix was designed.

Why were the first two fixes rejected?

Both were checked against the whole corpus before being written. Rejecting an end record whose offsets imply the archive starts after byte zero also fires on files with bytes inserted at the front — 294 cases. Adding a second condition still left 142. A fix for eight cases that mis-handles hundreds is not a fix.

Is the final rule a heuristic?

No. It skips an end-record candidate when its offset is exactly a validated embedded archive’s own end record, and continues scanning. There is no threshold, no score and no search — the offset either is that or it is not, decided by the same container map the engine already uses to refuse promoting nested local headers.
